# 场景需求分析：运行中动态修改 Node 参数

> 依据 `docs/01-需求分析.md` FR-DM-2、FR-RT-6。本文档只做需求分析，不涉及设计。

## 1. 场景背景

运行中的图需要调整节点行为，但不改变节点和边的拓扑。例如：

- 转码：调整码率、GOP、编码预设
- 合成：调整布局、窗口位置、透明度、字幕内容
- AI 推理：调整置信度阈值、NMS 阈值、合批超时
- 特效：调整美颜强度、滤镜参数、水印位置
- 通用：调整限流速率、队列容量、告警阈值

该能力与"替换节点/增删边"不同：目标是让参数变更低开销、不中断图数据流，并对每个 Packet 的处理语义有清晰边界。

## 2. 已确认口径

| 维度 | 决策 | 需求含义 |
|---|---|---|
| 生效边界 | **下一帧 / 下一个输入 Packet 生效** | 已入队和在途异步请求继续使用旧参数；从生效边界后的 Packet 使用新参数。单个 Packet 不允许混用新旧参数 |
| 原子范围 | **同一 Node 内多参数原子** | 一次请求可调整同一节点多个参数；下游只能观察到完整旧参数集或完整新参数集，不出现半新半旧 |
| 不支持热更 | **拒绝** | Node/算子声明可热更新参数集合；不支持原地更新的参数直接失败，节点与参数值保持不变，不自动重建节点 |
| 并发冲突 | **同一 Node 内串行** | 参数变更按提交顺序依次生效；后一次以已生效参数版本为基线。不同 Node 的变更可并行 |

## 3. 用户故事

- **US-PM1** 作为转码策略系统，我将编码节点的 `bitrate` 从 3M 调为 2.5M；本请求成功后，下一视频帧开始按新码率编码，正在编码的旧帧完整产出。
- **US-PM2** 作为会议系统，我一次更新合成节点内主讲窗口的位置、大小、层级；下一输出帧只能呈现旧布局或完整新布局，不能出现半更新、撕裂画面。
- **US-PM3** 作为算法策略系统，我修改推理节点的 `score_threshold` 与 `nms_threshold`；已提交到 GPU 的请求按旧阈值后处理，后续请求按新阈值处理，结果可通过参数版本追溯。
- **US-PM4** 作为调用方，我请求修改 `model_path`，但该节点声明不支持热更新；引擎拒绝请求，返回参数名、当前值、拒绝原因和可选替代操作（节点替换），不改变运行图。
- **US-PM5** 作为美颜控制端，我连续提交强度 `0.2 → 0.4 → 0.6`；引擎对该节点按提交顺序串行处理，最终状态为 `0.6`，每次变更都有独立结果与生效版本。
- **US-PM6** 作为运维，我查询节点当前参数与版本号，能够知道某一 Packet 使用的是哪一版参数，并审计谁在何时修改过参数。

## 4. 功能需求

### 4.1 参数能力声明

| 编号 | 需求 | 优先级 |
|---|---|---|
| PM-C-1 | 每个 Node/算子在元数据中声明参数 Schema：名称、类型、默认值、范围/枚举校验、是否可热更新 | P0 |
| PM-C-2 | 可热更新参数可声明生效语义，但首期统一要求支持"下一 Packet 生效"；不支持原地热更新的参数必须显式标记 | P0 |
| PM-C-3 | 参数 Schema 支持标量、字符串、数组、对象等结构化值，满足布局等复杂参数；结构体内部业务语义由算子解释 | P0 |
| PM-C-4 | Node 可选声明参数组合约束（如 `min_bitrate ≤ bitrate ≤ max_bitrate`、布局窗口不得重叠），变更请求按完整新参数集校验 | P1 |

### 4.2 参数更新接口与事务

| 编号 | 需求 | 优先级 |
|---|---|---|
| PM-U-1 | 提供程序化 API 与 patch 配置两种入口：指定 Node、一个或多个参数及新值 | P0 |
| PM-U-2 | 一次请求仅修改**同一 Node**；多个参数作为节点内原子事务提交 | P0 |
| PM-U-3 | 请求先做完整校验：Node 存在、参数存在、类型/范围合法、全部参数均支持热更新、组合约束满足；任一失败则整体拒绝、参数不变 | P0 |
| PM-U-4 | 成功请求分配单调递增的 `parameter_version`；变更结果返回该版本与实际生效边界（序号/PTS） | P0 |
| PM-U-5 | 提供 `GetParameters(node)` 查询当前完整参数快照与 `parameter_version` | P0 |
| PM-U-6 | 支持参数变更历史查询：请求来源、提交时间、旧值、新值、结果、生效边界与版本号 | P1 |

### 4.3 生效与一致性

| 编号 | 需求 | 优先级 |
|---|---|---|
| PM-E-1 | 参数更新成功后，从该 Node **下一个输入 Packet**开始使用完整新参数集；已入队、正在执行或已提交到异步后端的请求继续使用旧参数集 | P0 |
| PM-E-2 | 一个 Packet 的整个处理周期只能绑定一个 `parameter_version`；同步 Process、异步 Submit/完成事件、后处理均不得混用版本 | P0 |
| PM-E-3 | 多输入 Node 的参数变更以其下一次处理触发为界；该次触发读取一个完整参数快照 | P0 |
| PM-E-4 | 参数变更不得暂停、丢弃或重排不受影响的 Packet；对输出影响仅来自新参数本身的业务效果 | P0 |
| PM-E-5 | 输出 Packet 元数据可选附带 `parameter_version`，使下游/审计可关联该结果的参数版本 | P1 |

### 4.4 异步推理协同

| 编号 | 需求 | 优先级 |
|---|---|---|
| PM-A-1 | 异步推理 Node 在 Submit 时绑定参数快照及 `parameter_version`；该请求完成时继续按绑定版本执行后处理与结果标记 | P0 |
| PM-A-2 | 参数变更不取消、不修改已在合批队列/后端在途的请求；后续进入合批队列的请求使用新版本 | P0 |
| PM-A-3 | 合批聚合键必须区分影响模型执行语义的参数版本；不同 `parameter_version` 的请求不得混入同一 batch | P0 |
| PM-A-4 | 仅影响后处理的参数（如 score/NMS threshold）是否允许混批，由算子声明；默认按版本隔离，避免语义混淆 | P1 |

### 4.5 并发、队列与失败

| 编号 | 需求 | 优先级 |
|---|---|---|
| PM-Q-1 | 同一 Node 的参数变更请求严格按提交顺序串行；后一请求在前一请求生效/失败后处理 | P0 |
| PM-Q-2 | 不同 Node 的参数更新可以并行处理，互不阻塞 | P0 |
| PM-Q-3 | 每 Node 参数变更队列长度可配置，超限时拒绝新请求并返回资源忙；不得无限排队 | P1 |
| PM-Q-4 | 算子应用新参数失败（底层编码器 reconfigure / GPU 资源失败）时，本次变更整体失败并保留旧参数；失败不能影响正在运行的旧版本处理 | P0 |
| PM-Q-5 | 每次失败返回结构化错误：参数名、错误类型（不支持/校验失败/底层应用失败/队列繁忙）、当前参数版本及是否可重试 | P0 |

### 4.6 边界与替代路径

| 编号 | 需求 | 优先级 |
|---|---|---|
| PM-B-1 | 不支持原地热更新的参数（如模型路径、codec、端口定义、执行设备）必须拒绝，不得隐式重建 Node | P0 |
| PM-B-2 | 返回拒绝时可附带替代建议：调用方应使用节点替换/图变更事务；建议仅为信息，不自动执行 | P1 |
| PM-B-3 | 参数变更不支持跨 Node 原子性；需要多 Node 一致切换时，调用方使用图变更事务或上层编排 | P0 |

## 5. 非功能需求

| 编号 | 指标 | 目标 |
|---|---|---|
| PN-1 | 单 Node 参数请求校验与排队开销 | < 1ms（不含算子底层应用耗时） |
| PN-2 | 无需底层异步 reconfigure 的参数，从提交成功到下一 Packet 使用新参数 | ≤ 1 个 Packet 周期 + 1ms |
| PN-3 | 参数变更对不受影响节点/分支的调度影响 | 0 丢帧、无额外停顿 |
| PN-4 | 参数版本查询 | < 1ms |
| PN-5 | 同一 Node 连续 1,000 次参数修改后 | 无内存增长、无参数版本错配、审计记录完整 |

## 6. 约束

- 参数变更是**控制面操作**，不得在数据面热路径中解析 JSON/YAML、分配大量对象或持有全局锁。
- 业务自定义格式参数可作为透明对象传给算子，但引擎只负责整体原子替换与版本标识，不解析业务字段；Schema 层仅能做可声明的通用校验。
- 由于不自动重建 Node，算子开发者必须准确声明 `hot_updatable` 能力；声明支持但底层无法安全切换时视为算子缺陷。
- 跨 Node 的联动配置（如 Scale 输出分辨率与 Encoder 输入分辨率同时变化）不是本能力范围，必须使用已有图变更事务保证一致性。

## 7. 验收要点

- 下一帧边界：在帧 N 处理中提交变更，验证 N 使用旧版本、N+1 使用新版本，输出元数据可追溯。
- 节点内原子：一次修改布局的多个字段，逐帧录制输出，不出现半新半旧布局或撕裂。
- 异步绑定：先提交推理请求，再修改阈值；验证先提交结果用旧版本、后提交结果用新版本，合批不得混入不同版本请求。
- 拒绝与回滚：修改模型路径/codec 等不支持项、组合约束非法值、底层 reconfigure 失败，均验证参数快照保持不变。
- 串行：同一 Node 快速提交 1,000 次变更，结果版本严格单调、最终参数等于最后一次请求；不同 Node 可并行完成。
