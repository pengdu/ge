# 图引擎（Graph Engine）需求分析

## 1. 项目背景与目标

### 1.1 背景

音视频处理与深度学习推理场景（直播、点播转码、实时美颜/特效、视频理解、多路摄像头分析等）具有典型的流水线特征：数据在一系列处理单元之间按固定拓扑流转，各单元之间存在天然的并行性。现有方案（如 FFmpeg filter graph、GStreamer、MediaPipe、DeepStream）各有侧重，难以同时满足：

- 音视频 + AI 推理统一编排
- 运行中动态修改图结构（热插拔、热更新）
- 高并发多路会话共享算力
- 配置文件与 API 双通道构图

### 1.2 目标

构建一个通用、可嵌入的图执行引擎（以下简称 GE），使业务方能够：

1. 以有向图描述音视频处理 / AI 推理流水线
2. 通过配置文件或编程 API 构建、启动、修改、销毁图
3. 在多核 CPU / 多 GPU / NPU 环境下获得接近硬件上限的吞吐
4. 同时服务大量并发会话（数百至数千路）
5. 在不中断数据流的前提下动态修改正在运行的图

### 1.3 非目标

- 不实现具体编解码器、模型推理框架，仅做集成（FFmpeg、TensorRT、ONNX Runtime、OpenVINO 等作为算子后端）
- 不提供分布式跨机调度（首期单机，预留扩展接口）
- 不提供图形化编辑器（可在后续基于配置文件格式开发）

## 2. 术语定义

| 术语 | 说明 |
|---|---|
| Graph（图） | 由节点和边组成的有向图，描述一条完整处理流水线 |
| Node（节点）/ Operator（算子） | 图中的处理单元，如解码、缩放、推理、编码 |
| Edge（边）/ Stream | 节点间的数据通道，带缓冲队列 |
| Port（端口） | 节点的输入/输出插槽，边连接在端口上 |
| Packet（数据包） | 在边上流动的数据单元，携带时间戳与元数据 |
| Session（会话） | 一个图实例及其运行上下文，对应一路业务流 |
| Calculator/Kernel | 算子的具体实现，可有 CPU/GPU 等多后端 |
| Scheduler（调度器） | 决定何时、在哪个线程/设备上执行节点 |
| Graph Mutation（图变更） | 运行时对图的增删节点/边、参数修改操作 |

## 3. 用户与使用场景

### 3.1 用户角色

| 角色 | 需求 |
|---|---|
| 算法工程师 | 快速用配置文件拼装推理流水线，验证效果 |
| 业务开发工程师 | 通过 SDK API 在服务中嵌入图引擎，动态构图 |
| 算子开发者 | 按规范实现新算子并注册到引擎 |
| 运维 / SRE | 监控图运行状态、性能指标，排查瓶颈 |

### 3.2 典型场景

**场景 A：直播实时特效**
RTMP 拉流 → 解封装 → 视频解码 → 人脸检测(GPU) → 关键点 → 美颜/贴纸(GPU) → 编码 → 推流；音频路径并行：解码 → 降噪 → 编码。要求端到端延迟 < 100ms，主播开关特效时动态插入/移除节点。

**场景 B：视频批量转码 + 内容审核**
文件读取 → 解码 → 多分辨率缩放（1 → N 分支）→ 多路编码；同时旁路抽帧 → 分类 / OCR / NSFW 检测 → 结果聚合。要求吞吐最大化，GPU 利用率 > 85%。

**场景 C：多路摄像头 AI 分析**
数百路 RTSP 流共享同一批推理模型，要求跨会话动态 batching，单卡支撑尽可能多路数。

**场景 D：语音处理**
麦克风采集 → VAD → ASR → NLU → TTS → 播放，节点间为变长数据，要求低延迟流式处理。

**场景 E：A/B 实验与模型热更新**
线上运行中将某推理节点的模型版本从 v1 切换到 v2，或按流量比例分流到两个子图，不能断流。

## 4. 功能需求

### 4.1 图模型（FR-GM）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-GM-1 | 支持有向图，允许多入多出节点、扇入/扇出 | P0 |
| FR-GM-2 | 支持 DAG 和带反馈环的图（反馈环需显式声明，用于状态回传，如跟踪器） | P1 |
| FR-GM-3 | 支持子图（Subgraph）封装与复用，子图可嵌套 | P0 |
| FR-GM-4 | 节点端口支持类型契约：内置类型可做严格校验；自定义数据使用业务命名的逻辑类型标签（如 `biz.UserProfile@v1`）做**标签相等性**校验。引擎不解析、不注册、不依赖其数据结构 | P0 |
| FR-GM-5 | 支持边上的可选属性：队列容量、背压策略（阻塞/丢弃最旧/丢弃最新）、同步策略 | P0 |
| FR-GM-6 | 支持 Source / Sink / Transform / Mux / Demux / Tee 等基础节点类型 | P0 |
| FR-GM-7 | 支持条件路由 / Switch 节点，按 Packet 内容动态选择下游 | P1 |
| FR-GM-8 | 支持图级别与节点级别的参数（Options），参数可带默认值与校验规则 | P0 |
| FR-GM-9 | 图校验：环路检测、悬空端口检测、类型不匹配检测、参数校验，返回结构化错误 | P0 |
| FR-GM-10 | Node 必须导出机器可读能力与人可读功能描述；构图/图变更时上下游端口按逻辑类型、格式、内存/设备、同步语义协商并冻结边契约。无共同能力集时拒绝，禁止隐式插入转换节点 | P0 |
| FR-GM-11 | 一个输出 Port 支持扇出到多个下游；共享输出能力必须满足所有下游需求的公共交集。交集为空时拒绝，调用方显式插入 Tee 与分支转换；每条扇出边有独立队列与背压策略 | P0 |

### 4.2 构图方式（FR-BD）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-BD-1 | 支持配置文件构图，格式：YAML / JSON（首期），预留 protobuf text 格式 | P0 |
| FR-BD-2 | 配置文件支持变量、模板、include 引用子图文件、环境变量替换 | P1 |
| FR-BD-3 | 提供 C++ 原生 API（Builder 模式）构图 | P0 |
| FR-BD-4 | 提供 C API 及 Python 绑定 | P1 |
| FR-BD-5 | 配置文件与 API 构建结果等价，可互相导出（API 构图可 dump 为配置文件） | P1 |
| FR-BD-6 | 支持图模板 + 参数实例化，同一模板创建多个会话 | P0 |
| FR-BD-7 | 提供 Schema 文件用于配置文件校验与编辑器提示 | P2 |

**配置文件示例（YAML，仅示意）：**

```yaml
graph: live_beauty
version: 1
options:
  gpu_id: 0
nodes:
  - name: src
    type: RtmpSource
    options: { url: "${INPUT_URL}" }
  - name: vdec
    type: VideoDecoder
    options: { hw: cuda }
  - name: face_det
    type: TrtInference
    options: { model: models/face_v2.plan, batch: 8, batch_timeout_ms: 5 }
  - name: beauty
    type: BeautyFilter
  - name: venc
    type: VideoEncoder
    options: { codec: h264_nvenc, bitrate: 4M }
  - name: sink
    type: RtmpSink
    options: { url: "${OUTPUT_URL}" }
edges:
  - src.video -> vdec.in
  - vdec.out -> face_det.in
  - vdec.out -> beauty.frame
  - face_det.out -> beauty.faces
  - beauty.out -> venc.in
  - venc.out -> sink.video
  - { from: src.audio, to: sink.audio, queue: { cap: 64, policy: drop_oldest } }
```

| 编号 | 需求 | 优先级 |

| 编号 | 需求 | 优先级 |

| FR-SC-2 | 多种线程模型：全局线程池 / 按节点独占线程 / 按设备（CPU、GPU、NPU）分池；节点可指定执行器 | P0 |

## 5. 非功能需求

### 5.1 性能（NFR-P）

| 编号 | 指标 | 目标 |
|---|---|---|
| NFR-P-1 | 框架调度开销 | 单节点单 Packet 调度开销 < 2 µs（不含算子计算） |
| NFR-P-2 | 端到端附加延迟 | 10 节点线性图，框架引入延迟 < 50 µs（CPU 空载） |
| NFR-P-3 | 吞吐 | 1080p 解码→缩放→推理→编码 流水线，单 GPU（T4 级）≥ 硬件编解码上限的 90% |
| NFR-P-4 | 并发会话 | 单机（32 核 / 1 GPU）稳定运行 ≥ 500 路 720p 分析流（推理受限场景） |
| NFR-P-5 | GPU 利用率 | 推理密集型场景 ≥ 85% |
| NFR-P-6 | 内存 | 零稳态内存增长；每会话固定开销 < 2 MB（不含帧缓冲） |
| NFR-P-7 | 动态变更 | 单次图变更完成时间 < 10 ms，受影响路径暂停 < 1 帧周期 |
| NFR-P-8 | 启动 | 100 节点图构建+校验+初始化（不含模型加载）< 50 ms |

### 5.2 可靠性（NFR-R）

- 单个节点崩溃（异常）不导致进程崩溃，可按策略隔离或重启节点
- 单个会话故障不影响其他会话
- 7×24 连续运行无资源泄漏（文件描述符、内存、显存、线程）
- 关闭与销毁在任何状态下均能在有界时间内完成（不死锁、不悬挂）

### 5.3 可扩展性（NFR-E）

- 新增算子无需修改引擎核心
- 新增设备后端（如 NPU）通过执行器与内存分配器接口扩展
- 新增配置格式通过 Parser 接口扩展
- 预留分布式扩展：边可实现为跨进程/跨机传输（RPC/共享内存），图语义不变

### 5.4 可用性（NFR-U）

- 错误信息定位到配置文件行号 / API 调用点，附带修复建议
- 完善的文档：架构、算子开发指南、配置文件参考、API 参考
- 示例工程覆盖 3.2 中各场景

### 5.5 兼容性（NFR-C）

- 语言：核心 C++17/20；绑定 C、Python 3.8+
- 平台：Linux x86_64（P0）、Linux aarch64（P1）、Windows / macOS（P2）
- 加速：CUDA 11+ / TensorRT 8+（P0）、OpenVINO、Ascend、RKNN（P2）
- 构建：CMake，可作为静态库/动态库嵌入

### 5.6 安全（NFR-S）

- 配置文件解析防注入（环境变量替换限白名单）
- 插件加载校验（签名可选）
- 运行时控制 API 可接入鉴权（宿主提供）

## 6. 接口需求概要

## 6.1 数据契约：内置类型与透明自定义数据

- **内置类型**（VideoFrame / AudioFrame / Tensor 等）：引擎理解其基础元数据，可做端口严格类型校验、内存池与设备迁移优化。
- **透明自定义数据**：使用者以业务类型标签声明端口契约（例如 `chat.Message@v2`、`biz.UserProfile@v1`），Packet payload 可为 TXT、bytes 或任意 C++ 对象。引擎只比较标签是否相等并负责引用生命周期，不读取 payload 内部字段，也不要求把自定义格式/结构体引入或注册到框架。
- 自定义数据在同进程内沿边传递时，发送与接收算子共享业务定义即可；引擎不承担跨版本解释、格式转换或业务语义校验。若未来跨进程/设备，业务方需可选提供序列化与重建钩子（FR-DT-7）。

### 6.2 构图 API（C++ 示意）

```cpp
GraphBuilder b("live_beauty");
auto src  = b.AddNode("RtmpSource", "src", {{"url", url}});
auto dec  = b.AddNode("VideoDecoder", "vdec", {{"hw", "cuda"}});
auto det  = b.AddNode("TrtInference", "face_det", {{"model", "face_v2.plan"}});
b.Connect(src["video"], dec["in"]);
b.Connect(dec["out"], det["in"]);
GraphSpec spec = b.Build();               // 静态描述，可序列化
auto graph = Engine::Instance().Create(spec);
graph->Start();
```

### 6.2 动态变更 API

```cpp
auto tx = graph->BeginMutation();
tx.RemoveEdge("vdec.out", "venc.in");
auto blur = tx.AddNode("GaussianBlur", "blur", {{"sigma", 3.0}});
tx.AddEdge("vdec.out", "blur.in");
tx.AddEdge("blur.out", "venc.in");
tx.SetOption("venc", "bitrate", "6M");
Status s = tx.Commit();                   // 原子提交，失败自动回滚
```

### 6.3 算子接口

```cpp
class MyOp : public Operator {
  static OpSpec Spec();                   // 端口、参数 Schema、能力声明
  Status Open(Context&) override;
  Status Process(Context&) override;      // 从输入端口取 Packet，向输出端口发 Packet
  Status Close(Context&) override;
  Status OnOptionChanged(const std::string& key, const Value& v) override;  // 热更新
};
REGISTER_OPERATOR(MyOp);
```

### 6.4 控制与观测 API

- `graph->GetTopology()`、`graph->GetStats()`、`graph->Pause()/Resume()/Stop()`
- `Engine::ListGraphs()`、`Engine::LoadPlugin(path)`
- 指标 `/metrics` 端点由宿主暴露，引擎提供 Collector

## 7. 约束与假设

- 引擎运行在单进程内，多会话共享线程池与 GPU；跨机由上层调度系统负责
- 算子开发者需遵循线程安全约定：`Process` 可能被并发调用当且仅当算子声明为无状态
- 首期不支持图变更的跨会话事务（一次变更只作用于一个图实例）
- 帧率、分辨率等媒体参数的运行时变化由算子自行处理（引擎透传元数据）

## 8. 风险分析

| 风险 | 影响 | 应对 |
|---|---|---|
| 动态变更与高性能调度冲突（锁竞争） | 变更时抖动、吞吐下降 | 采用 RCU / 版本化拓扑快照，调度器读无锁，变更写侧构建新版本后原子切换 |
| 跨会话 batching 增加尾延迟 | 实时场景延迟不达标 | batch 超时可按会话优先级配置；实时会话可关闭合批 |
| GPU 内存碎片 | 长时间运行后 OOM | 分级显存池 + 预分配 + 碎片整理时机（空闲期） |
| 第三方算子质量不可控 | 崩溃、泄漏拖垮进程 | 异常捕获边界、看门狗、可选进程级隔离 |
| 配置文件与 API 语义漂移 | 两条路径行为不一致 | 二者统一落到同一 `GraphSpec` 中间表示 |
| 反馈环导致死锁 | 图卡死 | 环路边强制非阻塞 + 初始 Packet 注入语义 |

## 9. 里程碑建议

| 阶段 | 范围 | 验收 |
|---|---|---|
| M1 核心引擎 | 图模型、Spec、校验、静态图调度、Packet/内存抽象、基础算子（Tee/Mux、文件 I/O、FFmpeg 编解码） | 场景 B 无 AI 部分跑通，性能达 NFR-P-1/2 |
| M2 异构与推理 | GPU 执行器、显存池、零拷贝、TensorRT/ORT 推理算子、动态 batch | 场景 B 完整跑通，GPU 利用率达标 |
| M3 动态图 | 变更事务、RCU 拓扑切换、热更新参数、节点替换 | 场景 A、E 跑通，NFR-P-7 达标 |
| M4 高并发 | 跨会话 batching、优先级调度、背压、会话隔离 | 场景 C 达 NFR-P-4 |
| M5 生态 | Python 绑定、Prometheus/Trace、插件系统、文档与示例 | 全场景示例可运行 |

## 10. 待确认问题

1. 首期目标硬件平台与 GPU 型号？是否需要国产 NPU 支持？
2. 并发会话规模的实际业务目标（数百 vs 数千路）？
3. 动态修改图的调用方是人（运维）还是程序（自动策略），对变更延迟的真实容忍度？
4. 是否需要跨进程/跨机图（如解码与推理分离部署）？决定边抽象的设计深度。
5. 配置文件是否需要兼容已有格式（如 MediaPipe pbtxt、GStreamer pipeline 字符串）？
6. 宿主语言主要是 C++ 还是 Python，决定 API 优先级。
