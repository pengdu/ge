# 图引擎详细设计

> 依据 `00-需求规格说明书.md` 与 `02-架构设计.md`。本文细化核心数据结构、稳定 C ABI、运行时状态机和关键算法。Node 执行接口采用**回调式**。

## 1. 设计约束

1. 数据面只读取已发布的 `RuntimeTopology`，不获取控制面全局锁。
2. Node 不主动拉取 Port；引擎准备好输入后，通过回调把输入 Packet 交给 Node。
3. Node 同步输出通过 Host 提供的 `emit` 回调；异步输出只能投递 `CompletionQueue`。
4. C ABI 边界只允许 POD、opaque handle、长度明确的 Buffer/JSON，禁止 STL、异常、虚表和跨侧释放 C++ 对象。
5. 同一 Packet 在处理周期内绑定 `topology_version` 和 `parameter_version`。

## 2. 核心数据结构

### 2.1 标识与版本

```cpp
using GraphId = uint64_t;
using SessionId = uint64_t;
using NodeId = uint64_t;
using EdgeId = uint64_t;
using PacketSeq = uint64_t;
using TopologyVersion = uint64_t;
using ParameterVersion = uint64_t;
using OperationId = uint64_t;
using PluginId = uint64_t;
```

- `TopologyVersion` 在 Session 内单调递增；每次成功发布 Mutation 加一。
- `ParameterVersion` 在 Node 内单调递增；每次成功参数热更新加一。
- `PacketSeq` 由 Source 或 Session 级序列器分配；异步请求必须保留原始 seq。

### 2.2 Packet 与 Buffer

```cpp
struct PacketHeader {
  PacketSeq seq;
  int64_t pts_ns;
  int64_t dts_ns;
  uint32_t flags;
  TopologyVersion topology_version;
  ParameterVersion parameter_version;
  TypeTagId type_tag;
};

struct Packet {
  PacketHeader header;
  MetadataRef metadata;
  BufferRef payload;
};

struct Buffer {
  void* data;
  size_t size;
  MemoryKind kind;          // host / pinned / cuda_device / dmabuf
  int32_t device_id;
  std::atomic<uint32_t> refs;
  BufferDeleter deleter;
  void* deleter_context;
};
```

- `TypeTagId` 指向注册表中的内置类型或业务逻辑标签（如 `biz.UserProfile@v1`）。透明类型仅比较标签，不解析 payload。
- `BufferRef` 是侵入式引用计数。扇出只增加 Buffer 引用，不复制 payload。
- metadata 为小对象优化的键值表；热路径常用字段（格式、错误、dropped/timeout）使用预定义 key。

### 2.3 EdgeChannel

```cpp
struct EdgeConfig {
  uint32_t capacity;
  DropPolicy policy;        // block / drop_oldest / drop_newest
  SyncPolicy sync_policy;   // aligned / latest / any
};

struct EdgeChannel {
  EdgeId id;
  ConnectionContract contract;
  EdgeConfig config;
  BoundedQueue<PacketRef> queue;
  std::atomic<EdgeState> state;
  EdgeMetrics metrics;
};
```

- 每条 Edge 独立队列、背压和指标。
- 首期优先使用 SPSC 环形队列；存在多个上游生产者时，在构图阶段插入 Mux Node 或选择 MPSC 实现，不能隐式假定线程安全。
- `block` 不允许永久占用 GPU 回调线程；该场景由调度器把 Node 标记为 backpressured 并延迟再次调度。

### 2.4 NodeRuntime

```cpp
struct NodeRuntime {
  NodeId id;
  OperatorKey operator_key;            // type@version
  OperatorHandle plugin_handle;
  CapabilityDescriptor capability;
  AtomicSharedPtr<ParameterSnapshot> parameters;
  std::atomic<NodeState> state;
  uint32_t max_parallelism;
  std::atomic<uint32_t> in_flight;
  ResourceLease lease;
  NodeMetrics metrics;
};
```

状态：`created → opening → ready → running → draining → closing → closed / failed`。

- 有状态 Node：`max_parallelism=1`。
- 无状态 Node：可配置并行；每个回调带独立输入批次和参数快照。
- Node Runtime 不保存可变拓扑；输入/输出路由由所属 `RuntimeTopology` 提供。

### 2.4a EdgeState 与 SessionState

```cpp
enum class EdgeState : uint8_t {
  active,        // 正常收发
  backpressured, // 队列满且策略为 block；上游禁止继续生产
  draining,      // 所属拓扑已 retired，只允许消费不允许生产
  retired        // 队列已空或 fast 清空，等待释放
};

enum class SessionState : uint8_t {
  created, starting, running, pausing, paused,
  stopping, stopped, failed
};
```

EdgeState 迁移：

- `active → backpressured`：`try_push` 失败且 `policy == block`。
- `backpressured → active`：`Pop` 释放槽位后由 Scheduler 在重新 MarkReady 上游前切换。
- `active/backpressured → draining`：所属 RuntimeTopology 进入 retired list 且 `remove_policy == drain`。
- `active/backpressured/draining → retired`：Drain 完成（队列空且下游 in_flight=0）或 Fast 清空。
- `draining/retired` 下 `Push` 返回 `GE_STATUS_CANCELLED`。

SessionState 迁移：

- `created → starting → running`：`ge_session_start`；Node 全部 `ready` 后进入 running。
- `running → pausing → paused`：`ge_session_pause`；Source 停止拉取，Edge 保持，已在途请求完成。
- `paused → running`：`ge_session_resume`。
- `running/paused → stopping → stopped`：`ge_session_stop`；`fast_shutdown=0` 走 Drain，`=1` 走 Fast。
- 任意状态 `→ failed`：`REL-1` 阈值触发或不可恢复内部错误；失败后只允许 `stop/destroy`。
- Mutation 与参数更新仅在 `running`/`paused` 接受；其余状态返回 `GE_STATUS_INVALID_ARGUMENT` 并附当前状态。

### 2.5 RuntimeTopology 与 Session

```cpp
struct RouteEntry {
  EdgeChannelRef edge;
  ConnectionContract contract;   // 与 edge.contract 相同，冗余用于无锁读取
};

// 输出 Port → 下游 Edge 列表（扇出）；发布后不可变。
using RouteTable = FlatMap<PortId, std::vector<RouteEntry>>;

// 输入 Port → 所属 InputBinding；发布后不可变。
using InputBindingTable = FlatMap<NodeId, InputBinding>;

struct RuntimeTopology {
  TopologyVersion version;
  std::vector<NodeRuntimeRef> nodes;
  std::vector<EdgeChannelRef> edges;
  RouteTable routes;
  InputBindingTable inputs;
  std::vector<PluginLease> plugin_leases;
  std::vector<ResourceLease> resource_leases;
};

struct RetiredTopology {
  std::shared_ptr<RuntimeTopology> topology;   // 强引用，保证在途工作可完成
  RemovePolicy policy;
  Deadline drain_deadline;
  std::vector<NodeId> removed_nodes;
  std::vector<EdgeId> removed_edges;
};

// 按 retire 顺序排列；条目在 removed_* 全部 closed/retired 且 AsyncRuntime
// 报告该 topology_version 在途请求为 0 后移除。
using RetiredTopologyList = std::deque<RetiredTopology>;

// 同 Session 的 Mutation FIFO；仅 MutationCoordinator 线程消费。
using MutationQueue = BoundedQueue<MutationRequest>;

struct Session {
  SessionId id;
  AtomicSharedPtr<RuntimeTopology> current_topology;
  MutationQueue mutations;
  std::atomic<SessionState> state;
  SessionMetrics metrics;
  RetiredTopologyList retired;
  CompletionSinkRef completion_sink;   // 见 §3.5
};
```

`TopologyLease` 是 `PluginLease` 与 `ResourceLease` 的统称（02-架构设计 §3.1），不是独立类型。

- `RuntimeTopology` 发布后其 Node/Edge/RouteTable 不再修改。
- `RetiredTopologyList` 保存等待 Drain、异步请求归零或引用释放的旧快照。
- Session 通过原子 acquire 读取 current topology，执行回调时持有强引用，保证发布后旧快照仍可安全完成在途工作。

## 3. 回调式稳定 C ABI

> 本章只说明 ABI 语义与约束。结构体字段、函数签名的**唯一权威定义**在 `13-接口与类设计.md` §3–§5；本章代码片段与 13 冲突时以 13 为准。

### 3.1 ABI 演进规则

所有 C ABI 结构体首字段：

```c
typedef struct ge_struct_header {
  uint32_t struct_size;
  uint32_t abi_major;
} ge_struct_header;
```

- 同 major 仅允许在结构体尾部追加字段和追加函数表成员。
- 调用方传入的 `struct_size` 小于当前版本时，仅访问共同前缀。
- 所有返回内存的所有权必须明确：调用方 Buffer 由调用方释放；Host 创建的 Buffer 通过 Host API retain/release。

### 3.2 插件描述与创建

```c
typedef struct ge_operator_descriptor {
  ge_struct_header header;
  const char* type_name;
  const char* semantic_version;
  const char* capability_json;
  const char* parameter_schema_json;
  const char* functional_description;
  const struct ge_operator_vtable* vtable;
  uint32_t flags;
  uint32_t max_parallelism;
  uint64_t max_inference_ms;
} ge_operator_descriptor;

typedef struct ge_plugin_descriptor {
  ge_struct_header header;
  const char* plugin_id;
  const char* build_fingerprint;
  const char* manifest_json;
  const ge_operator_descriptor* operators;
  uint32_t operator_count;
} ge_plugin_descriptor;

typedef const ge_plugin_descriptor* (*ge_plugin_get_descriptor_fn)(
    uint32_t requested_abi_major);

typedef ge_status (*ge_plugin_create_operator_fn)(
    const struct ge_operator_create_args* args,
    ge_operator_handle* out_operator);
```

每个 `type@version` 的 vtable 由其 `ge_operator_descriptor` 直接提供；引擎按 `args.operator_key` 选择 descriptor 并调用 `vtable->create`。so 级 `ge_plugin_create_operator` 导出函数为可选的兼容入口，语义等价于按 key 查 descriptor 后调用其 `vtable->create`。

manifest 与 descriptor 中能力信息交叉校验：type@version、ABI、端口、资源估算和最大推理时长不一致时拒绝加载。

### 3.3 Host API

```c
typedef struct ge_host_api {
  ge_struct_header header;
  ge_status (*buffer_retain)(ge_buffer_handle buffer);
  void (*buffer_release)(ge_buffer_handle buffer);
  ge_status (*buffer_get_view)(ge_buffer_handle buffer, ge_buffer_view* out_view);
  ge_status (*emit)(const struct ge_emit_args* args);
  ge_status (*completion_push)(ge_completion_sink_handle sink,
                                const struct ge_completion_event* event);
  ge_status (*event_publish)(const struct ge_event* event);
  void (*log)(const struct ge_log_record* record);
  ge_status (*buffer_alloc)(...);   /* ABI 1 尾部追加，见 13 §4.3 */
  ge_status (*buffer_wrap)(...);
} ge_host_api;
```

- `emit` 仅允许在同步 `process` 回调生命周期内调用。
- `buffer_alloc`/`buffer_wrap` 是插件获得输出 payload 的唯一途径：前者走引擎 Buffer 池，后者包裹插件自有内存并在引用归零时回调释放。
- `completion_push` 允许后端完成上下文调用；它只入队，不访问图对象。`sink` 来自 `ge_submit_request.completion_sink`，其生命周期见 §3.5。
- Host API 不暴露 RuntimeTopology、Session C++ 对象或 Executor 内部。

### 3.4 同步 Node 回调

```c
typedef struct ge_process_request {
  ge_struct_header header;
  ge_session_id session_id;
  ge_topology_version topology_version;
  ge_parameter_version parameter_version;
  uint32_t flags;                       /* GE_PROCESS_FLAG_* */
  const ge_packet_view* inputs;
  const char* const* input_ports;
  uint32_t input_count;
  const char* parameter_json;
  void* callback_context;
} ge_process_request;

typedef ge_status (*ge_operator_process_fn)(
    ge_operator_handle op, const ge_process_request* request);
```

`inputs[i]` 对应 `input_ports[i]`。Host API 指针在 `ge_operator_create_args.host_api` 中一次性交付并在 operator 生命周期内有效，不随每次请求重复传递。

引擎调用前完成：输入同步、参数快照选择、in_flight 增加、Node 状态校验。插件只处理给定输入，不访问其他 Port。

### 3.5 异步 Submit 回调

```c
typedef struct ge_submit_request {
  ge_struct_header header;
  ge_request_id request_id;
  ge_session_id session_id;
  ge_topology_version topology_version;
  ge_parameter_version parameter_version;
  ge_packet_seq packet_seq;
  const ge_packet_view* inputs;
  const char* const* input_ports;
  uint32_t input_count;
  const char* parameter_json;
  ge_completion_sink_handle completion_sink;
  /* ABI 1 尾部追加（12 §3.1）：batch 分帧，见下文 */
  uint64_t batch_id;
  uint32_t batch_index;
  uint32_t batch_size;
} ge_submit_request;

typedef ge_status (*ge_operator_submit_fn)(
    ge_operator_handle op, const ge_submit_request* request);
```

`ge_completion_sink_handle` 生命周期：

- 每个 Session 拥有一个 sink，由引擎在 Session 创建时分配、在 Session 销毁且 AsyncRuntime 确认无在途请求后释放。
- 同一 Session 内所有 `ge_submit_request` 携带同一 sink；插件可在 `submit` 返回后的任意线程持有并调用 `completion_push(sink, event)`，直到该请求的 completion 已投递。
- 对已销毁 sink 调用 `completion_push` 属于插件错误；引擎通过 `PLG-6` 的引用归零规则保证插件在 sink 释放前已无在途请求。

插件不得调用图回调、不得保存 Host API 中不保证异步有效的临时指针；若需保留输入，必须 `buffer_retain`。

`batch_id/batch_index/batch_size`（ABI 1 尾部追加）：同一 batch 的成员在同一提交线程上对同一实例背靠背调用 `submit`；插件按 `batch_id` 聚合、在最后一个 `batch_index` 发起后端调用并为每个 `request_id` 各 push 一条 completion。语义细节见 13 §4.6。

### 3.6 Completion Event

```c
typedef struct ge_completion_event {
  ge_struct_header header;
  ge_request_id request_id;
  ge_session_id session_id;
  ge_topology_version topology_version;
  ge_parameter_version parameter_version;
  ge_packet_seq packet_seq;
  ge_status status;
  const ge_packet_view* outputs;
  const char* const* output_ports;
  uint32_t output_count;
} ge_completion_event;
```

`status.code != GE_STATUS_OK` 时 `outputs` 可为空；错误详情通过 `status.detail_json` 携带，不另设 `error_json`。

Completion Queue 消费者按 session、topology、parameter、request 生命周期校验；不匹配事件丢弃并记录 `orphan_completion_total`。

## 4. Node 回调与路由

### 4.1 同步 Process

```text
Scheduler
  1. topology = session.current_topology.load(acquire)
  2. 输入绑定表取满足 sync 的 Packet 集合
  3. parameter = node.parameters.load(acquire)
  4. 创建 ProcessRequest(topology.version, parameter.version)
  5. 调 plugin.process(handle, request)
  6. plugin 经 host.emit 输出
  7. Host 根据 topology.routes 将 Packet 写入每个 Edge
  8. in_flight--，尝试再次标记 ready
```

`host.emit` 验证：

- callback_context 仍有效；
- 输出 Port 属于调用 Node；
- payload 类型匹配输出 Contract；
- Packet 继承当前 topology_version 与 parameter_version；
- 扇出 Edge 分别写入，按各自策略处理拥塞。

### 4.2 异步 Submit

- Scheduler 准备 SubmitRequest 后调用插件；插件提交 GPU 后立即返回。
- Batcher 启用时，Scheduler 先把请求交给 Batcher，等待不占 Executor。
- 完成后 Completion Queue 统一进入 AsyncRuntime。
- AsyncRuntime 仅在对应旧/当前拓扑仍处于可收尾状态时交付；若已 Fast 删除或 Session 已关闭，则丢弃。

### 4.3 CompletionQueue 与 AsyncRuntime 交付路径

```cpp
struct CompletionQueue {
  MpscBoundedQueue<CompletionEvent> events;   // 多生产者（后端线程）单消费者（AsyncRuntime）
  uint32_t capacity;                           // 默认 4096；满时 completion_push 返回 RESOURCE_EXHAUSTED
  std::atomic<uint64_t> dropped_on_full;
};

struct AsyncRequestEntry {
  RequestId id;
  SessionId session;
  TopologyVersion topology;
  ParameterVersion parameter;
  NodeId node;
  PacketSeq seq;
  Deadline deadline;                           // submit_time + max_inference_ms
  std::shared_ptr<RuntimeTopology> topology_ref; // 强引用，保证交付时拓扑存活
};

struct AsyncRuntime {
  CompletionQueue queue;
  FlatMap<RequestId, AsyncRequestEntry> in_flight;
  FlatMap<NodeId, ReorderBuffer> reorder;       // 按 (session, topology, node) 分片
};
```

AsyncRuntime 消费线程算法（每条 CompletionEvent）：

1. `entry = in_flight.find(event.request_id)`；找不到 → `orphan_completion_total++`，release 事件 payload，结束。
2. `entry.session/topology/parameter` 与事件字段不一致 → 同上视为 orphan。
3. `entry.topology_ref` 对应拓扑处于 `retired` 且 `policy == fast` → orphan。
4. `reorder[node].Insert(event.seq, event)`，按 §6.4 得到可交付的有序结果集。
5. 对每个可交付结果，按 `entry.topology_ref->routes` 调用 `PacketRouter.Emit(node, output_port, packet)`；PacketRouter 校验 output_port 属于 node、type_tag 匹配 Contract 后写入各下游 Edge。
6. `in_flight.erase`，`node.in_flight--`，`node.EndInvoke()`；若 node 状态为 `async_pending` 且 in_flight 归零则回到 `ready` 并尝试 MarkReady。
7. 处理完成后 `buffer_release` 事件 payload。

AsyncRuntime 是唯一调用 `PacketRouter.Emit` 处理异步输出的组件；同步 `emit` 由 HostApiAdapter 直接调用 PacketRouter。

### 4.4 EOS 传播

EOS 是带 `GE_PACKET_FLAG_EOS` 的空 payload Packet，沿 Edge 传播：

1. Source 报告 exhausted 后，Scheduler 对其每个输出 Port 发送一个 EOS Packet。
2. InputBinding 收到某 Port 的 EOS 后记录 `eos_ports.insert(port)`，该 Port 不再参与同步条件判断：
   - `any`：其余任一必需 Port 仍有数据即可触发；所有必需 Port 均 EOS 时判定为输入结束。
   - `latest`：EOS Port 视为"无最新值"，触发时不提供该 Port 的 Packet；所有必需 Port 均 EOS 时输入结束。
   - `aligned`：EOS Port 退出对齐窗口；基准 Port EOS 时立即输入结束，其余 Port 的残留 Packet 丢弃并计数。
3. 输入结束且 `in_flight == 0` → Node 进入 `draining`，Scheduler 调用一次 `flush` 语义的 `process`（`input_count == 0`，`flags` 含 `GE_PROCESS_FLAG_FLUSH`），Node 借此输出尾数据。
4. flush 返回后 Node 对每个输出 Port 发送 EOS，转 `closing → closed`，调用 `operator_close`。
5. 扇出时对每条下游 Edge 独立 Push EOS；EOS 不受 DropPolicy 丢弃：队列满时以 `block` 语义等待槽位。
6. Sink 收到全部必需输入 EOS 后执行 flush 并 closed；Session 内所有 Node closed 后 `stopped`。
7. 异步 Node：输入结束后等待 `in_flight` 归零（含 ReorderBuffer 排空）再执行第 3 步。

### 4.5 MediaFormatChanged 前沿传播

- 事件由产生新格式的 Node 在 `emit` 关键帧前通过 `event_publish` 发布，事件携带该关键帧 `seq`。
- HostApiAdapter 把事件作为带 `GE_PACKET_FLAG_EVENT` 的控制 Packet 插入同一输出 Edge 队列，位置紧邻其后的关键帧之前；因此 Edge FIFO 保证事件先于关键帧到达下游。
- InputBinding 遇到事件 Packet 时不参与同步，直接投递给 Node 的 `on_event`（P7 定义）；ReorderBuffer 中事件 Packet 与其 seq 绑定，随关键帧一并排序。
- 观察订阅收到的是事件副本，不影响上述数据面顺序。

## 5. 参数快照

```cpp
struct ParameterSnapshot {
  ParameterVersion version;
  JsonValue values;
  PacketSeq effective_after_seq;
};

// 每个 NodeRuntime 持有一个；控制面串行写，数据面无锁读。
struct ParameterStore {
  AtomicSharedPtr<ParameterSnapshot> current;
  std::shared_ptr<ParameterSnapshot> pending;     // 已校验、等待下一 Packet 边界切换
  SerialQueue<ParameterUpdateRequest> updates;     // 同 Node 串行；不同 Node 独立
  std::vector<ParameterAuditRecord> history;       // PAR-8，容量可配
};
```

- 更新请求先在控制面完整校验，生成 `version+1` Snapshot 放入 `pending`。
- Node 在下一次接收输入 Packet 时（`BeginInvoke` 前）原子切换 `current = pending`，`effective_after_seq = 该 Packet.seq`，写入审计。
- 异步请求、Batcher key、Completion Event 都保留提交时参数版本。
- 不支持热更新或插件应用失败，旧 Snapshot 保持不变，`pending` 清空。
- `pending` 非空时再次更新：新请求排队等待前一 pending 生效后再校验，保证 PAR-5 串行语义。

## 6. 调度、队列与背压

### 6.1 Ready 状态机

```text
              输入满足同步条件
Idle ─────────────────────────────→ Ready ── Executor 取走 ──→ Running
 ▲                                      │                         │
 │                                      │ CAS 失败（已入队）       │ 同步完成 / Submit 返回
 └──────────────────────────────────────┴─────────────────────────┘
                                                     │
                                                     ├─ 异步在途：AsyncPending
                                                     └─ EOS 且无待处理：Draining → Closed
```

```cpp
enum class NodeState : uint8_t {
  created, opening, ready, running, async_pending,
  draining, closing, closed, failed
};
```

- 单并行度 Node 用 `Idle → Ready` CAS 消除重复入队。
- 并行度 `N>1` 的无状态 Node 使用 `available_slots` 原子计数；每占一个 slot 入队一次。
- `ReadyQueue` 按 Executor 分区：CPU 使用 MPSC work queue，GPU 使用每 `device_id` 的 submit queue。
- GPU submit worker 只负责发起 CUDA/TRT/ORT 异步调用，不等待 GPU 完成。
- 完整的状态迁移、正交标志（held/retiring/cancelled/busy）、Invoke 决策树与文件布局见 `16-调度器状态机.md`。

### 6.2 Edge 写入与背压

```text
Emit(packet, edge):
  1. queue.try_push(packet)
  2. 成功：更新深度，尝试 MarkReady(target)
  3. 满队列：按 Edge DropPolicy 处理
     - drop_newest：丢弃当前 packet，计数
     - drop_oldest：原子弹出旧 packet，再尝试写当前 packet
     - block：不阻塞执行线程；标记 edge/node backpressured，返回 WOULD_BLOCK
  4. 聚合上游背压状态，供 Source/RateLimiter 查询
```

- `block` 的含义是"禁止继续生产"，不是持锁或睡眠等待。
- 同步 Process 内 emit 撞满 block 边时由引擎停放该 packet（对 Node 视为成功），下游腾出空位后按同边 FIFO 重推；Node 在停放清空前不再被调用。EOS 排在停放数据之后。机制细节见 `16-调度器状态机.md` §4。
- 每个 Edge 独立统计：`queue_depth`、`drop_count`、`would_block_count`、`max_depth`。

### 6.3 多输入同步

```text
InputBinding.try_acquire():
  any:     任一必需 Port 至少一个 Packet 即可触发
  latest:  消费触发 Packet；其余 Port 丢弃旧 Packet 并取最新可用 Packet
  aligned: 以触发 Packet PTS 为目标，在各 Port 取窗口内最接近 Packet
```

`aligned` 的规则：

1. 目标 PTS 取配置基准 Port 的头 Packet；未配置则取最早满足条件的必需输入。
2. 其他 Port 在 `±window_ns` 内找最接近 Packet。
3. 全部到齐立即返回；超时由 Node 指定补偿策略（冻结、黑帧、占位、跳过）。
4. 迟到 Packet 按 Node 策略丢弃或保留到下个窗口。

### 6.4 异步保序与缺口

```cpp
struct ReorderBuffer {
  PacketSeq next_expected;
  map<PacketSeq, CompletionResult> completed;
  Deadline head_deadline;
};
```

- 完成 seq 等于 `next_expected`：立即输出并连续 drain `completed`。
- 完成 seq 大于 `next_expected`：暂存并启动/保持 head deadline。
- deadline 到期：为缺失 seq 输出带 `dropped/timeout=true` 的逻辑缺口事件，`next_expected++`，继续 drain。
- 完成 seq 小于 `next_expected`：迟到结果，丢弃并记录。

## 7. Mutation 详细算法

### 7.1 请求模型

```cpp
struct MutationRequest {
  OperationId operation_id;
  SessionId session_id;
  TopologyVersion base_version;
  vector<MutationAction> actions;
  RemovePolicy remove_policy;      // drain / fast
  CallerContext caller;
};
```

`MutationAction` 包括：`AddNode`、`RemoveNode`、`InsertChain`、`RemoveChain`、`ReplaceNode`、`AddEdge`、`RemoveEdge`、`RemoveBranch`、`SetNodeOption`。对应 patch JSON 的 `action` 取值为其 snake_case 形式（`add_node`、`remove_node`、`insert_chain`、`remove_chain`、`replace_node`、`add_edge`、`remove_edge`、`remove_branch`、`set_node_options`）；`13-接口与类设计.md` §5.3 与本表以本表为准。

同一 Session 按 FIFO 进入 `MutationQueue`。在尚未开始 `Building` 前，兼容的请求可合并：

- **兼容判定**：队首连续的若干请求，`base_version` 均等于当前 `Vn` 或均为"最新"，`remove_policy` 相同，且任意两请求的 action 目标集合（NodeId/EdgeId/PortRef）两两不相交。任一条件不满足即停止合并。
- **合并方式**：按 FIFO 顺序把各请求的 `actions` 拼接为一个 `MergedMutationRequest`，记录 `origin_operations: vector<OperationId>`；Phase A 只构建一次候选拓扑。
- **结果映射**：合并请求成功 → 所有 origin operation → `succeeded`，共享同一 `Vn+1`；合并请求任一阶段失败 → 所有 origin operation → `failed`，错误详情标注触发失败的 action 及其原始 operation_id。不做部分成功。
- 合并上限默认 8 个请求，可配置。

### 7.2 两阶段执行

```text
Phase A：Prepare（失败不影响运行图）
  A1. 读取 current topology Vn
  A2. 以 Vn 对应 GraphSpec 复制 CandidateSpec
  A3. 应用 MutationAction
  A4. Validate CandidateSpec
  A5. 协商新增/受影响 Edge，生成 Candidate Contracts
  A5'. GraphDiff：以 (Vn spec, Vn contracts) 与 (candidate, candidate contracts)
       计算结构 diff，决定 Node/Edge 复用 vs 重建（见下）
  A6. ResourceManager.reserve()
  A7. 创建并 Open/预热新增或替换 Node
  A8. 组装 CandidateTopology Vn+1（复用集合只来自 A5'）

Phase B：Commit / Retire
  B1. CAS 发布 session.current_topology: Vn → Vn+1
  B2. 新 Packet 开始按 Vn+1 路由
  B3. 把 Vn 放入 retired list，标记被删 Node/Edge draining 或 fast
  B4. Drain 完成/fast 清理/异步在途归零
  B5. Close Node、释放 Edge/插件/资源租约
  B6. operation → succeeded
```

- A1–A8 任一失败：关闭已预热 Node、释放候选资源，operation → failed，`Vn` 不变。
- A5' `GraphDiff` 是 spec + contract 的纯函数，与产生候选的 action 序列无关。Node 按 id 分为 `kept / added / removed / replaced（同 id 换 operator@version）/ updated（同 operator，输入重接线、端口集、executor 或 parallelism 变化：NodeRuntime 复用，发布时 Rebind）`；Edge 按 id 分为 `kept / added / removed / recreated（端点、queue、feedback、数据面契约变化，或任一端 Node 被 replaced：换 channel，旧 channel 队列内包走完旧路径）`。`options` 变化不是拓扑变化。`RuntimeTopology::Build` 只信任 diff 给出的复用集合，不再自行比较契约；扇出契约的 `target_capability` 指纹变化不构成 recreated（BUG-01）。diff 随 `DryRunResult` 返回，并写入成功 operation 的 `detail.diff`，同时记录 `prepare_ms`（A2–A7）与 `retire_ms`（B1→B5）。
- B1 使用 base_version 校验；若当前版本已变，重新基于最新版构建或返回 `VERSION_CONFLICT`。
- B1 后不能回滚到 Vn；收尾失败只影响 retired 资源释放与告警，不影响 Vn+1 数据面。

### 7.3 连续 Node 链插入

```text
InsertChain(U.out, D.in, [N1, N2, ..., Nk])

CandidateSpec:
  remove U.out → D.in
  add U.out → N1.in
  add N1.out → N2.in
  ...
  add Nk.out → D.in
```

约束：

- Node 链有序，链首/链尾 Port 必须明确；不依赖端口名称猜测。
- 每条新 Edge 生成 Contract；全部成功才进入预热。
- 发布后旧 Edge 标记 retired；其已入队 Packet 走旧 Edge 到旧下游，新的 Packet 走完整新链，禁止半链。

### 7.4 连续 Node 链删除与 bypass

`RemoveChain([N1...Nk], mode)`：

- `disconnect`：调用方已提供后续 AddEdge/RemoveEdge 使 CandidateSpec 合法。
- `bypass`：要求 N1 有唯一外部输入、Nk 有唯一外部输出、链内节点和 Edge 均专属线性路径。

```text
CandidateSpec bypass:
  remove U.out → N1.in
  remove chain internal edges
  remove Nk.out → D.in
  remove N1...Nk
  add U.out → D.in
```

新 bypass Edge 必须重新协商 Contract。以下情况拒绝 bypass：

- 任一 Node 有额外必需输入、输出或外部引用；
- Node/Edge 被其他分支共享；
- U.out 与 D.in 无公共能力集；
- 删除会生成非法环、悬空必需 Port 或资源状态冲突。

### 7.5 替换 Node

`ReplaceNode(old, new_type@version, mapping)`：

1. `mapping` 显式定义旧/新 Port 映射；未提供时仅允许同名 Port 一一映射。
2. 按 Schema 迁移声明为 `migratable` 的参数；其他参数由请求提供或使用新默认值，缺少必需参数则拒绝。
3. 保留旧连接但重新协商所有入/出 Edge。
4. 预热新 Node 成功后发布；旧 Node 停止接收新 Packet，按 remove_policy 收尾。

### 7.6 删除分支

`RemoveBranch(entry_edge, selected_nodes)`：

1. 从入口 Edge 沿目标方向遍历候选子图。
2. 只允许删除入度/出度均局限在候选集内的专属 Node/Edge。
3. 遇到连接候选集外的共享 Node/Edge，停止扩展并返回 `SHARED_DEPENDENCY` 及依赖列表。
4. CandidateTopology 移除分支 Route；公共上游 RouteTable 保留其他下游。
5. 发布后分支 Drain/Fast，不影响公共路径。

### 7.7 Drain 与 Fast

```text
Drain:
  停止向 retired Edge 写新 Packet
  等待 Edge queue 为空、Node in_flight=0、AsyncRequest=0
  向下游注入 EOS（需要封装尾数据的 Sink）
  到达 deadline 后升级 Fast 并上报

Fast:
  标记 retired Node/Edge cancelled
  清空 Edge queue、释放 PacketRef
  后续 Completion Event 视为 orphan，丢弃
  Close Node、释放租约
```

Drain 默认 deadline 由场景配置，转码分支默认 2s。

Drain 的推进与超时由 `MutationCoordinator` 的 Retire 阶段管理：

- B3 把 `RetiredTopology{policy=drain, drain_deadline=now+timeout}` 放入 `RetiredTopologyList` 后，Coordinator 订阅 `EdgeChannel` 空队列事件与 `NodeRuntime.EndInvoke` 归零事件；每次事件到达重新检查 §7.7 Drain 完成条件，满足即进入 B5。
- Engine 级 `Watchdog` 线程以 10ms 周期扫描所有 Session 的 `RetiredTopologyList`；发现 `now >= drain_deadline` 且未完成的条目，将其 `policy` 改为 `fast`、发布 `DrainTimeout` 事件并按 Fast 分支执行。
- 升级 Fast 时正在执行的同步 `process` 不被中断；Fast 只清空队列并拒绝其后续 `emit`（返回 `GE_STATUS_CANCELLED`），该 `process` 返回后 Node 直接 `closing`。
- Drain 期间 retired Node 收到的新 Packet 只能来自同一 retired 拓扑的上游；`Vn+1` 的路由不再指向它们。

## 8. 能力协商算法

### 8.1 约束表示

每个 Port Capability 归一化为以下约束维度：

```text
PortConstraints
  logical_type: exact tag | builtin type family
  video: pixel_formats, width_range, height_range, fps_range,
         color_spaces, color_ranges, hdr_modes
  audio: sample_formats, sample_rate_range, channel_layouts
  tensor: dtypes, layouts, shape constraints
  memory: memory_kinds, device_ids, zero_copy_required
  sync: supported sync policies
  priority: ordered preference list
```

- 输出 Port 提供集合/范围；输入 Port 声明可接受集合/范围。
- 透明自定义数据只比较 `logical_type` 精确标签；其他 payload 字段不参与协商。
- 未声明的内置格式维度视为“不受约束”，但必需维度不能由双方都缺失。

### 8.2 单 Edge 协商

```text
Negotiate(output_cap, input_cap, preferences):
  1. 校验方向与 logical_type
  2. 按媒体/音频/Tensor 类型选择适用维度
  3. 求每个维度 intersection
  4. intersection 为空：返回 Conflict(dimension, lhs, rhs)
  5. 对多候选项按：调用方 preference → 输入 Port priority → 输出 Port priority → 稳定字典序 选择
  6. 生成 ConnectionContract
```

伪代码：

```cpp
Result<ConnectionContract> negotiate(const PortCapability& out,
                                     const PortCapability& in,
                                     const PreferenceSet& pref) {
  require(out.direction == Output && in.direction == Input);
  require(type_compatible(out.logical_type, in.logical_type));

  ContractBuilder result;
  for (Dimension dim : applicable_dimensions(out, in)) {
    CandidateSet common = intersect(out.supported(dim), in.accepted(dim));
    if (common.empty()) return conflict(dim, out, in);
    result.set(dim, choose_deterministically(common, pref, out, in));
  }
  return result.build();
}
```

`Conflict` 至少包含：Edge、两端 Node/Port、冲突维度、双方候选集合/范围、推荐显式转换 Node 类型。

### 8.3 扇出公共契约

对输出 Port `O` 与下游集合 `{I1...In}`：

```text
common = O.capability
for each Ii:
  common = intersect(common, Ii.accepted_capability)
  if common empty: report FanoutConflict(O, all consumers, failed dimension)
contract = choose_deterministically(common)
```

- 所有下游共享同一 `ConnectionContract`。
- 下游连接添加顺序不得影响结果；下游列表按稳定 NodeId/PortId 排序后协商。
- Mutation 新增扇出时，必须验证原 Contract 仍包含在新公共集合中；否则拒绝变更，不自动修改既有下游格式。

### 8.4 协商缓存与失效

```cpp
struct NegotiationCacheKey {
  OperatorKey source_operator;
  CapabilityVersion source_capability;
  OperatorKey target_operator;
  CapabilityVersion target_capability;
  PortId source_port;
  PortId target_port;
  PreferenceHash preferences;
};
```

- 缓存值仅为候选 Contract，不含 Node Runtime 状态。
- 插件加载/逻辑卸载、能力描述更新、优先级配置变化时失效对应 key。
- Mutation 仍需对候选 Contract 做最终端口/资源校验，缓存不绕过校验。

## 9. 插件 Registry 详细设计

### 9.1 manifest

裸 so 的同目录 manifest 采用 JSON，示意：

```json
{
  "plugin_id": "com.example.vision",
  "abi": {"major": 1, "minor": 2},
  "library": "libexample_vision.so",
  "build_fingerprint": "clang-18-linux-x86_64",
  "dependencies": [{"name": "tensorrt", "version": "8.6"}],
  "resources": ["models/detector.plan"],
  "operators": ["Detector@2.0.0"],
  "max_inference_ms": 100
}
```

加载校验顺序：

```text
白名单路径 → manifest JSON → ABI major → 宿主依赖版本 → dlopen →
plugin_get_descriptor → manifest/descriptor 一致性 → operator 注册冲突 → 注册完成
```

任何一步失败：关闭已打开句柄、保留结构化错误、不得修改 Registry。

### 9.2 插件状态机

```text
Discovered → Validating → Loading → Registered → Active
                                     │             │
                                     │             ├→ Retiring → LogicallyUnloaded
                                     │             │                  └→ PhysicallyUnloaded (optional)
                                     └→ Rejected
```

| 状态 | 含义 | 新建 Node | 既有引用 |
|---|---|---|---|
| Registered / Active | 可解析 type@version | 允许 | 允许 |
| Retiring | 停止接受新引用 | 拒绝 | 允许完成/迁移 |
| LogicallyUnloaded | 注册表不可见，so 句柄保留 | 拒绝 | 必须为零 |
| PhysicallyUnloaded | 已显式 dlclose | 拒绝 | 必须为零 |
| Rejected | 校验或加载失败 | 拒绝 | 无 |

### 9.3 引用模型与一键联动替换

```cpp
struct PluginReference {
  PluginId plugin_id;
  OperatorKey key;
  SessionId session_id;
  NodeId node_id;
  TopologyVersion topology_version;
};
```

- RuntimeTopology 发布时增加其中 Node 的 PluginLease。
- retired topology 完成收尾时释放 Lease。
- Completion Event 的在途计数属于对应 PluginLease 的释放前置条件。

一键替换：

```text
UpgradeAndRetire(old type@version, new type@version):
  1. old → Retiring，禁止新建引用
  2. snapshot(old references)，按 Session 分组
  3. 每个 Session 提交 ReplaceNode Mutation
  4. 收集 per-session 成功/失败结果
  5. 全部成功且 old references = 0：LogicalUnload(old)
  6. 任一失败：old 保持 Retiring/Active（按调用参数），返回聚合结果
```

不提供跨 Session 原子回滚。已成功替换的 Session 不回退。

### 9.4 默认逻辑卸载与可选物理卸载

逻辑卸载始终执行：移除 `type@version` 解析入口、释放插件可释放缓存/模型实例、保留 `dlopen` 句柄。

物理卸载仅当显式 `request_physical_unload=true` 且满足：

- PluginLease、NodeRuntime、AsyncRequest、CompletionQueue 事件均为零；
- 插件声明 `no_owned_threads=true`，引擎线程探测通过；
- 无活跃计时器、注册回调或跨边界对象；
- `operator_close/destroy` 已完成。

任一条件不满足时返回 `PLUGIN_PHYSICAL_UNLOAD_UNSAFE`，逻辑卸载状态不回退。

## 10. 资源管理详细设计

### 10.1 资源账本

```cpp
enum class ResourceKind {
  cpu_threads, host_memory, pinned_memory, gpu_memory,
  cuda_streams, nvdec_sessions, nvenc_sessions, edge_buffer_bytes
};

struct ResourceAmount { ResourceKind kind; int32_t device_id; uint64_t amount; };
struct ResourceLease { LeaseId id; SessionId owner; vector<ResourceAmount> amounts; };
```

- 资源账本按 `(ResourceKind, device_id)` 管理 `capacity/reserved/used`。
- `reserve()` 在控制面持有资源管理器细粒度锁，采用全有或全无：任一资源不足，已暂留项全部回滚。
- 预热成功后 `commit(lease, actual)` 调整估算值；实际超出可用量时预热失败并回滚，不挤占运行会话。
- 资源不足不进行抢占、优先级排序或自动降级。

### 10.2 资源准入路径

```text
Estimate(Node/Edge chain)
  → aggregate candidate resources
  → ResourceManager.reserve(all)
  → Node Open / model load
  → report actual
  → commit lease
  → topology publish
```

资源错误返回：资源类型、设备、请求量、已用量、保留量、总容量、可用量、建议重试条件。

### 10.3 Edge Buffer 预算

每 Edge 在构图时计算：

```text
queue_buffer_budget = capacity × max_packet_size
```

- `max_packet_size` 来自 Contract 格式、Node 能力或调用方显式上限。
- 无法估算且未配置上限时拒绝创建，防止无限内存承诺。
- Buffer 实际池使用量单独记录；预算用于准入，实际水位用于告警。

## 11. 统一错误模型

```cpp
struct ErrorDetail {
  ErrorCode code;
  Severity severity;
  bool retryable;
  string message;
  JsonValue context;
};
```

`ErrorCode` 与 `13-接口与类设计.md` §3.1 的 `ge_status_code` 一一对应；下表中 `ASYNC_ORPHAN_RESULT`、`OPERATION_CANCELLED` 分别映射为 `GE_STATUS_INTERNAL`（仅内部计数，不对外返回）与 `GE_STATUS_CANCELLED`。

| 错误码 | 场景 | 是否可重试 |
|---|---|---|
| `GRAPH_INVALID` | 拓扑、悬空 Port、非法环 | 否 |
| `VERSION_CONFLICT` | Mutation base topology 已过期 | 是 |
| `CAPABILITY_CONFLICT` | 端口/扇出无公共能力 | 否，需显式转换或重构 |
| `SHARED_DEPENDENCY` | 删除分支/链包含共享依赖 | 否，需指定范围 |
| `RESOURCE_EXHAUSTED` | 准入资源不足 | 是 |
| `NODE_WARMUP_FAILED` | Open、模型加载、外部连接失败 | 视底层错误 |
| `PARAMETER_UNSUPPORTED` | 不支持原地热更新 | 否，使用 Mutation |
| `PARAMETER_APPLY_FAILED` | 底层 reconfigure 失败 | 视底层错误 |
| `PLUGIN_ABI_MISMATCH` | C ABI major/结构不兼容 | 否 |
| `PLUGIN_MANIFEST_INVALID` | manifest/descriptor 不一致 | 否 |
| `PLUGIN_RETIRED` | 请求已 retiring/unloaded 的版本 | 否，选择其他版本 |
| `PLUGIN_PHYSICAL_UNLOAD_UNSAFE` | dlclose 前置条件未满足 | 是/可保持逻辑卸载 |
| `ASYNC_ORPHAN_RESULT` | 旧拓扑/会话的迟到结果 | 否，内部计数 |
| `OPERATION_CANCELLED` | Stop/Fast 取消后置操作 | 否 |

## 12. 观测、事件与审计结构

### 12.1 Metrics


### 12.2 事件

```cpp
enum class EventKind : uint8_t { data_plane, observation };
enum class EventType : uint16_t {
  eos, error, media_format_changed, node_failed, node_retried,
  drop, stall, clock_jump, connection, reconnection,
  mutation_state, parameter_applied, plugin_state, drain_timeout
};

struct Event {
  uint64_t event_id;
  EventKind kind;
  EventType type;
  Severity severity;
  SessionId session; NodeId source_node;
  int64_t timestamp_ns;
  std::optional<PacketSeq> seq; std::optional<int64_t> pts_ns;
  JsonValue detail;
};
```

C ABI 视图 `ge_event`（13 §5.4）字段与上述一致，`detail` 以 `detail_json` 传递。

`EventBus`：

- 数据面事件由 HostApiAdapter/Scheduler 直接沿 Edge 传递（§4.4/§4.5），不经过 EventBus。
- 观察事件：`EventBus.Publish(event)` 为每个匹配 filter 的 subscription 复制一份并 `try_push` 到其有界队列（默认 1024）；满则 `dropped_events++`，不阻塞。
- `ObserverExecutorPool` 每 subscription 一个串行任务链；取消订阅后队列剩余事件丢弃。

```cpp
// 每个 (Session, NodeRuntime) 一个实例；ge_host_api 函数表通过 host_context 找回它。
```
