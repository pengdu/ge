# 场景需求分析：动态增删转码链路

> 依据 `docs/01-需求分析.md`。本文档只做需求分析，不涉及设计。

## 1. 场景背景

转码输出档位（rendition ladder：同一输入源派生出的 1080p/720p/480p 等多档输出）在直播/点播运营中不是固定的：

- 观众人数、带宽、终端分布实时变化，最优档位集合随之变化
- CDN 回执显示某档位无人观看 → 下线该档位以节省编码算力
- 突发流量（活动开始、热门直播间）→ 临时增加档位
- 运营策略调整码率、水印、编码参数

传统的做法是整条流重启（重新拉流重建整图），代价是全档位中断数秒。本场景要求**在转码运行中，对档位链路做增、删、改而不中断服务**。

## 2. 已确认的需求口径

| 问题 | 结论 | 对需求的影响 |
|---|---|---|
| 触发方式 | **事件驱动**：CDN 回执/带宽事件自动触发，变更频率高且不可预测 | 变更必须是 API/程序化操作，不能依赖人工；变更本身的开销与抖动必须很小；需考虑变更风暴（短时间内大量档位变化）的合并与限流 |
| 删除模式 | **排空删除 与 快速删除 两种都要，可配置** | 删除行为按档位/场景配置；需要定义两种模式各自的语义边界 |
| 流连续性 | **多档位一致**：变更瞬间所有档位（含未变的）都不断流、不花屏 | 这是本场景最严格的要求：档位级变更不得影响其他档位输出；秒级连续切换档位也能无缝播放 |
| 规模 | **单机、小规模**（几十路会话，变更可串行执行） | 不要求变更并发调度的极致性能，优先正确性与语义清晰；单次变更完成时间可放宽到百毫秒级 |

## 3. 用户故事

- **US-1** 作为运营系统，当 CDN 回执显示某档位连续 N 分钟无人观看时，我要调用接口删除该档位，使 GPU 编码资源立即（或排空后）释放，且其余档位观众完全无感知。
- **US-2** 作为运营系统，当观众带宽统计显示需要 480p 档时，我要调用接口新增该档位，从提交到该档位可被拉流播放的时间不超过数秒（取决于 CDN 就绪，非引擎）。
- **US-3** 作为运营系统，我要把某档位码率从 3M 调到 2.5M，调整期间该档位输出不中断、不产生无法解码的帧。
- **US-4** 作为运营系统，我要把某档位 codec 从 H.264 切换到 H.265，切换期间观众侧要么看到完整 H.264 流要么看到完整 H.265 流，无黑屏窗口超过一个 GOP。
- **US-5** 作为运维，我要在变更后随时查询当前所有档位及其状态（编码中/排空中/已下线），并导出当前生效的完整配置用于复现。
- **US-6** 作为运维，当一次变更失败（如 CDN 连接失败、显存不足）时，我要引擎回滚到变更前状态，且已确认的失败原因明确可查。
- **US-7** 作为业务方，我在新增一路新源（整条会话）时，不能影响既有会话的变更与运行。

## 4. 需求范围界定

两个粒度，需求不同：

| 粒度 | 含义 | 是否本场景核心 |
|---|---|---|
| **档位级** | 运行中的图内增删改一条 `Scale→Encode→Mux→Sink` 分支 | **核心** |
| **会话级** | 新增/销毁一条完整源（含全部档位） | 边界内，但属通用生命周期需求（见 01 文档 FR-RT），本文不展开 |

## 5. 功能需求

### 5.1 新增档位

| 编号 | 需求 | 优先级 |
|---|---|---|
| TR-A-1 | 提交一次新增档位请求：档位参数（分辨率、码率、codec、GOP、水印等）+ 输出地址 | P0 |
| TR-A-2 | 新档位从当前输入帧开始工作，不要求回溯历史帧、不重拉源 | P0 |
| TR-A-3 | 新档位输出流可独立起播：首帧为关键帧（IDR），后续流内 GOP 结构完整 | P0 |
| TR-A-4 | 新档位的时间戳与源保持单调关系，**音画同步偏差 ≤ 40ms**（验收：ffprobe 逐帧比对 PTS/DTS） | P0（多档位一致性） |
| TR-A-5 | **新增期间，既有档位（含其观众）完全无感知**：无丢帧、无输出空档、无花屏 | P0（多档位一致性） |
| TR-A-6 | 新增失败（编码资源不足、输出连接失败等）自动回滚，既有图与既有档位不受影响 | P0 |
| TR-A-7 | 支持一次请求同时新增多个档位（一批为最小生效单元） | P1 |
| TR-A-8 | 变更风暴限流：**会话内合并**——同一会话的变更请求排队串行合并执行；跨会话各自独立、互不阻塞。排队期间返回"处理中"状态而非阻塞 | P1 |

### 5.2 删除档位

| 编号 | 需求 | 优先级 |
|---|---|---|
| TR-D-1 | 支持两种删除模式，按档位配置：**排空**（存量帧编完、封装尾数据写完整、输出连接正常关闭后才释放资源）/ **快速**（立即停止并释放资源，接受尾部丢帧） | P0 |
| TR-D-2 | 两种模式下，删除期间其余档位完全无感知 | P0 |
| TR-D-3 | 排空模式的完成必须以事件通知（资源已释放），不能只有"已受理" | P0 |
| TR-D-4 | 排空模式设置超时上限，超时降级为快速删除，降级事件需上报 | P0 |
| TR-D-5 | 删除后资源真实归还（编码器句柄、显存、内存），可被后续新增档位立即使用 | P0 |
| TR-D-6 | 排空模式下输出内容的完整性可被外部校验：**FLV（previousTagSize 尾标记完整）与 MP4（moov 完整可播放）纳入验收**；HLS 切片收尾（ENDLIST/切片对齐）为 P2 | P1 |
| TR-D-7 | 删除最后一档时行为可配置（允许图空转 / 拒绝删除） | P1 |

### 5.3 修改档位

| 编号 | 需求 | 优先级 |
|---|---|---|
| TR-U-1 | 码率、GOP、水印图片等参数修改：档位输出不中断，不产生无法解码的帧 | P0 |
| TR-U-2 | 分辨率修改：输出不中断，首帧参数变化处有关键帧/干净切换点 | P0 |
| TR-U-3 | codec 切换（H.264↔H.265）：中间态不可见——任一时刻该档位输出恰好为一种完整可播的流，**黑屏/不可播窗口 ≤ 500ms**（绝对时间指标，需切换点强制 IDR + 切片对齐） | P0 |
| TR-U-4 | 参数超出该档位允许范围时拒绝修改并返回原因，原值保持 | P0 |
| TR-U-5 | 一次请求可同时修改同一档位的多个参数（原子生效，不出现半新半旧组合） | P0 |
| TR-U-6 | 运行中**反复插入/删除滤镜 Node**（叠加文字、logo 等）：滤镜作为独立 `VideoFilter` Node 插到 scale→encode 之间（MUT-1a 链插入），删除时 bypass 复原；该档位编码器/封装器不重开、不丢帧、PTS 单调，其余档位无感知；滤镜链参数可热更新；非法滤镜串在预热期拒绝、原图不变 | P0 |

### 5.4 一致性需求（多档位一致，贯穿 A/D/U）

| 编号 | 需求 | 优先级 |
|---|---|---|
| TR-C-1 | 任一档位变更期间，其余档位：零丢帧（帧号可校验连续）、输出空档不超过编码器正常输出间隔 | P0 |
| TR-C-2 | 变更不影响其余档位的时间戳连续性与音画同步 | P0 |
| TR-C-3 | 观众在变更期间在多档位间切换播放（ABR 自适应码率），播放器侧无需特殊处理 | P1 |

### 5.5 操作与状态

| 编号 | 需求 | 优先级 |
|---|---|---|
| TR-O-1 | 全部增删改操作提供程序化 API；事件驱动系统按回执触发，无需人工 | P0 |
| TR-O-2 | 操作返回受理结果（成功/失败+原因）；排空等异步完成的过程提供状态查询与完成通知 | P0 |
| TR-O-3 | 任意时刻可查询：档位清单、每档位状态（编码中/新增预热中/排空中/下线）、当前生效参数 | P0 |
| TR-O-4 | 当前生效的档位配置可导出为配置文件，重放该配置可得到相同图（可复现性） | P1 |
| TR-O-5 | 增删改操作需要权限/来源标识（事件自动触发不应与人共用同一入口时需区分） | P2 |
| TR-O-6 | 会话级操作（整路新建/下线）与档位级操作可并行发起，互不阻塞、互不破坏 | P1 |

## 6. 非功能需求（本场景专项）

| 编号 | 指标 | 目标 | 备注 |
|---|---|---|---|
| TN-1 | 单次档位变更从提交到拓扑生效 | < 100 ms（不含编码器初始化、CDN 建连等外部耗时） | 小规模口径放宽于全局 NFR-P-7 的 10ms |
| TN-2 | 新增档位从提交到首帧输出 | < 1 s + 编码器初始化实际耗时 | 外部耗时需在状态中体现为独立阶段 |
| TN-3 | 排空删除完成时间 | 事件驱动，无固定上限；超时上限默认 2 s（可配），超时降级快删 | |
| TN-4 | 变更期间既有档位帧丢弃 | 0 | 可用帧号连续性自动校验 |
| TN-5 | 变更期间既有档位处理延迟劣化 | < 5% | |
| TN-6 | 资源释放延迟（删除完成到资源可复用） | < 100 ms | |
| TN-7 | 持续变更下的稳定性 | 每会话每分钟 1 次增删，24h 无死锁、无句柄/显存泄漏、吞吐无衰减 | 事件驱动高频验证 |

## 7. 开放问题（已全部决策）

| # | 问题 | 决策 | 落地 |
|---|---|---|---|
| Q1 | 音画同步偏差量化 | **≤ 40ms**，验收用 ffprobe 逐帧比对 PTS/DTS | TR-A-4 指标已定 |
| Q2 | codec 切换黑屏窗口 | **绝对时间指标：≤ 500ms**，不按 GOP 定；需编码器切片对齐配合 | TR-U-3 更新为绝对值 |
| Q3 | 排空删除尾数据格式 | **FLV + MP4** 两种纳入验收；HLS 切片收尾（ENDLIST/切片对齐）列为 P2 | TR-D-6 范围已定 |
| Q4 | 档位暂停中间态 | **不引入**：只有排空/快速两模式；事件抖动由上层防抖（回执持续 N 分钟才删） | 无新增需求 |
| Q5 | 编码器并发上限 | **数据中心 GPU（T4/A10/L4 级）**，NVENC 并发 30+，编码资源不足为非常态错误路径；消费级卡不支持 | TR-A-6 按低频错误处理 |
| Q6 | 变更风暴合并粒度 | **会话内合并**：同一会话的变更请求排队串行合并执行，跨会话各自独立、互不阻塞 | TR-A-8 语义已定 |
| Q7 | 引擎重启后状态恢复 | **外部重建**：档位状态以运营系统为准，引擎重启后由外部全量重建；引擎不持久化、无状态一致性问题 | 无持久化需求 |

### 7.1 决策补充说明

- **Q2 黑屏窗口 500ms**：codec 切换期间输出必须在 500ms 内从"完整旧流"过渡到"完整新流"，超短于典型 GOP（2s），意味着切换点需要强制编码器重新出 IDR + 切片对齐，而不是等下一个自然 GOP 边界。
- **Q7 外部重建**要求引擎把"全量重建一路会话"的耗时做到足够低（模板实例化 + 预热），这是外部重建方案可行的前提，已体现在 TC-S4 的创建速率要求中。

## 8. 验收要点（需求级，不绑定实现）

- 既有档位无感知：变更期间录制既有档位输出，帧号/时间戳连续无跳变，无花屏
- 新增档位独立可播：首帧 IDR、起播正常、音画同步达标（待 Q1）
- 排空删除：输出文件完整可播（待 Q3）、资源归还可被复用（再新增成功）
- codec 切换：全程探测该档位输出，任何时刻流可解析可播
- 回滚：构造 CDN 建连失败、显存不足，既有图帧号连续无影响
- 稳定性：TN-7 持续变更压测通过

## 9. 纯透传（remux）

编码流直通场景（对标 `ffmpeg -c copy`）：`MediaDemux` 的 `EncodedVideo`/`EncodedAudio` 输出直接连 `MediaMux` 的同名输入，不经过 decode/encode，即完成容器转换（mp4↔flv↔mkv）：

```
MediaDemux ──video (EncodedVideo)──▶ MediaMux
     └──────audio (EncodedAudio)──────▶┘
```

契约：demux 在每个出包上设置 `AVPacket::time_base` 为源 stream 的 time_base，mux 端 `AddStream`/`Write` 据此建立 stream time_base 并 rescale duration（`VideoEncode` 产出的包同样携带该字段，两条路径契约一致）。混合模式（视频直通 + 音频转码）、网络推流转发不在本场景范围。

验收：输出包数/时间戳序列与源逐包一致、codec 未变、文件完整可播（`MediaRemuxTest` 全套）。
