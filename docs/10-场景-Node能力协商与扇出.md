# 场景需求分析：Node 能力导出、上下游协商与扇出

> 依据 `docs/01-需求分析.md` FR-GM-4/FR-GM-5、FR-OP-2。本文档只做需求分析，不涉及设计。

## 1. 场景背景

Node 不能只声明静态的输入/输出类型；在媒体与异构处理场景中，Node 需要导出自身可处理、可生成和可执行的能力。例如：

- 解码 Node 可输出 NV12 或 P010、1920×1080@30fps 或 1280×720@60fps、Host 或 CUDA Device 内存
- 编码 Node 只接受 NV12、特定尺寸范围、特定 GPU 内存、H.264/H.265 参数集合
- 缩放 Node 可接受多种输入格式，但输出受其硬件/配置限制
- 通用 Node 对透明自定义数据不理解内部结构，但仍需要用端口逻辑类型标签约束上下游

构图或动态图变更时，引擎应让上下游 Node 根据端口能力协商出可行的连接契约；无法达成契约时必须在提交前失败，而不是运行后出现格式错误。一个输出端口允许连接多个下游 Node（扇出），但共享输出必须同时满足所有下游的需求。

## 2. 已确认口径

| 维度 | 决策 | 需求含义 |
|---|---|---|
| Node 能力导出范围 | **端口契约、媒体格式、执行与资源、功能元数据** | Node 的能力描述不仅用于校验，也用于外部查询、调试、资源准入与算子选择 |
| 协商时机 | **仅构图与图变更阶段** | 运行时格式变化不触发重新协商，仍遵循 `08-场景-运行期事件通知.md` 的关键帧绑定格式事件 |
| 不匹配策略 | **拒绝并要求显式转换** | 引擎不隐式插入 Scale/Convert/Resample 等 Node；调用方必须显式建图，拓扑可见、可审计 |
| 扇出协商 | **公共交集** | 一个上游输出对多个下游的共享输出契约必须是各下游可接受集合的交集；交集为空则构图/变更失败 |

## 3. 用户故事

- **US-N1** 作为构图方，我查询 `VideoDecoder@2.0` 的能力，能看到输入/输出端口、支持 NV12/P010、尺寸范围、帧率范围、Device/Host 内存、资源估算和功能描述。
- **US-N2** 作为构图方，我连接 Decoder 输出与 Encoder 输入时，引擎在 Build 阶段选择一个双方均支持的格式契约，生成可查询的协商结果。
- **US-N3** 作为构图方，Decoder 输出 P010，但 Encoder 仅支持 NV12 时，引擎拒绝连接并指出不匹配字段与候选能力；我显式插入 `ColorConvert` 后重新构图成功。
- **US-N4** 作为构图方，一个 Decoder 输出同时连接美颜（要求 RGBA）与编码（要求 NV12）；公共交集为空，因此引擎拒绝；我显式用 Tee 后分别接 `Convert(NV12→RGBA)` 与原始 NV12 分支。
- **US-N5** 作为运行系统，我动态新增一个下游编码档位时，引擎仅对新增边和受影响端口重新协商；如果新档位与现有共享输出无公共交集，本次变更整体失败，既有分支继续运行。
- **US-N6** 作为自定义业务算子开发者，我传递 `biz.UserProfile@v1` 的透明对象，不需要把其结构注册到框架；Node 通过相同逻辑类型标签完成端口协商。

## 4. 功能需求

### 4.1 Node 能力描述

| 编号 | 需求 | 优先级 |
|---|---|---|
| CAP-D-1 | 每个 Node/算子导出机器可读的 `CapabilityDescriptor`，可通过 C++/C API 查询，并随 so 元数据注册 | P0 |
| CAP-D-2 | 端口契约：端口名、输入/输出方向、必需性、基数（单/多）、是否支持运行中增减、逻辑数据类型标签、同步语义 | P0 |
| CAP-D-3 | 媒体能力：视频像素格式、宽高/范围、帧率/范围、色彩空间/范围、HDR；音频 sample format、采样率/范围、声道布局；Tensor dtype/shape/layout 等 | P0 |
| CAP-D-4 | 执行与资源能力：支持设备（CPU/GPU 与 device_id 限制）、可接受/输出内存类型（Host/Pinned/Device 等）、零拷贝能力、最大并行度、资源估算 | P0 |
| CAP-D-5 | 功能元数据：算子 type@version、功能描述、功能标签、参数 Schema、是否有状态、是否异步、是否支持热更新、支持的运行期事件 | P0 |
| CAP-D-6 | 透明自定义数据端口只需声明业务逻辑类型标签（如 `biz.UserProfile@v1`）及可选 payload 类别（text/bytes/object）；引擎不得要求其字段 Schema、序列化格式或 C++ 结构定义 | P0 |
| CAP-D-7 | 描述中每项能力可标注：固定值、可选集合、数值范围、依赖约束；能力描述支持版本号，以便审计协商结果对应的算子版本 | P1 |

### 4.2 协商时机与产物

| 编号 | 需求 | 优先级 |
|---|---|---|
| CAP-N-1 | 引擎仅在 Build、Validate、Create、图变更提交前进行能力协商；运行中不主动重新协商 | P0 |
| CAP-N-2 | 每一条边协商产出不可变 `ConnectionContract`：最终逻辑类型、媒体/Tensor 格式、内存类型/设备、同步语义、协商涉及的 Node 能力版本 | P0 |
| CAP-N-3 | 已协商契约是运行期该边的唯一格式依据；运行期格式变化仍按关键帧事件通知机制处理，不改变协商规则 | P0 |
| CAP-N-4 | 图配置导出与运行时查询必须能返回每条边的 `ConnectionContract`，便于复现与诊断 | P1 |
| CAP-N-5 | 图变更仅重新协商新增/删除/修改边和受影响扇出端口；变更失败不得改变既有 `ConnectionContract` | P0 |

### 4.3 双节点端口匹配

| 编号 | 需求 | 优先级 |
|---|---|---|
| CAP-M-1 | 输出端口能力与输入端口需求按维度求交集：逻辑类型、媒体/Tensor 格式、内存类型、设备、同步语义；全部必需维度存在可行解才可连接 | P0 |
| CAP-M-2 | 透明自定义数据的匹配规则为逻辑类型标签精确相等；引擎不尝试根据 payload 结构推导兼容性 | P0 |
| CAP-M-3 | 媒体能力匹配必须包含像素格式/尺寸/帧率/色彩空间等声明维度；任一必需字段不兼容即失败 | P0 |
| CAP-M-4 | 匹配存在多个可行解时，必须按确定性规则选择（由配置指定优先项或 Node 预设优先级）；相同输入产生相同 `ConnectionContract` | P0 |
| CAP-M-5 | 无可行解时拒绝 Build/变更，返回结构化诊断：边、两端 Node/Port、冲突能力维度、双方候选集合/范围、建议的显式转换类型 | P0 |
| CAP-M-6 | 引擎不得隐式插入转换 Node；调用方显式加入 Scale/ColorConvert/Resample/MemoryCopy 等转换后重新协商 | P0 |

### 4.4 一路输出到多个下游 Node（扇出）

| 编号 | 需求 | 优先级 |
|---|---|---|
| CAP-F-1 | 一个输出 Port 支持连接一个或多个下游输入 Port；多个下游可来自同一或不同 Node | P0 |
| CAP-F-2 | 上游输出与每个下游独立计算候选能力；共享输出 `ConnectionContract` 必须选择**所有下游需求集合的公共交集** | P0 |
| CAP-F-3 | 扇出公共交集为空时，拒绝整个 Build/变更，并返回各下游需求及造成交集为空的冲突维度 | P0 |
| CAP-F-4 | 引擎不为扇出自动生成格式不同的分支；调用方必须显式插入 Tee 与各分支转换 Node，使不同格式分支在图拓扑中可见 | P0 |
| CAP-F-5 | 公共交集存在多个候选时，使用 CAP-M-4 的确定性选择规则；不得因下游连接添加顺序不同而产生不同结果 | P0 |
| CAP-F-6 | 扇出数据语义：同一输出 Packet 可零拷贝分发给多个下游；每条边拥有独立的有界队列、背压策略与消费进度。某一慢下游的丢弃/拥塞不得修改其他下游已接收的 Packet | P0 |
| CAP-F-7 | 扇出下游数支持运行中通过图变更增减；新增下游触发 CAP-N-5 的扇出重协商，若公共交集缩小导致现有契约不可保持则拒绝变更 | P0 |
| CAP-F-8 | 扇出允许为每个下游边设置独立队列容量、背压/丢弃策略；上游与扇出整体的背压聚合规则需可配置并可观测 | P1 |

### 4.5 观察与审计

| 编号 | 需求 | 优先级 |
|---|---|---|
| CAP-O-1 | 能力查询接口可返回指定 `type@version` 的完整描述与人可读功能说明 | P0 |
| CAP-O-2 | 每次协商的输入能力、选择规则、最终契约、失败诊断写入图构建/变更审计记录 | P0 |
| CAP-O-3 | 运行时查询图拓扑时返回 Node 功能描述、端口能力摘要、边协商契约、扇出下游清单与边队列指标 | P1 |

## 5. 非功能需求

| 编号 | 指标 | 目标 |
|---|---|---|
| CN-1 | 100 Node / 300 Edge 图的全量能力协商与校验 | < 50ms（不含 Node Open/资源预热） |
| CN-2 | 动态新增一个扇出下游的增量协商 | < 5ms（不含节点预热） |
| CN-3 | 协商结果确定性 | 相同 GraphSpec、Node 版本、能力描述和优先配置下，100% 得到字节等价的 ConnectionContract |
| CN-4 | 能力查询 | < 1ms（已加载算子） |

## 6. 约束与边界

- 协商仅在控制面执行；运行数据面只读取已冻结的 `ConnectionContract`，不得为协商持锁或动态扫描能力。
- 运行期分辨率等格式变化是码流事实，不是重新协商请求；由 `08-场景-运行期事件通知.md` 中的节点能力响应机制处理。
- Node 能力描述必须诚实：声明支持但运行中无法处理，视为算子缺陷；引擎负责在构图期校验声明，不替代运行期错误处理。
- 透明自定义数据的"兼容"完全由业务端口标签表示；若用户将不兼容对象使用相同标签连接，属于业务契约违约，引擎不解析或拦截。

## 7. 验收要点

- 查询：读取媒体、资源、功能、端口四类能力，验证与 so 元数据/实际 Node 声明一致。
- 双端匹配：NV12 Decoder → NV12 Encoder 成功；P010 → 仅 NV12 Encoder 被拒，错误含冲突字段与 `ColorConvert` 建议；显式插入转换后成功。
- 透明数据：两个 `biz.UserProfile@v1` 端口连接成功，不要求注册结构；`v1` 到 `v2` 被拒。
- 扇出成功：NV12 Decoder 同时连接两个接受 NV12 的下游，协商得到同一契约；两边队列独立，阻塞一边不篡改另一边已消费数据。
- 扇出失败：现有 NV12 输出新增仅接受 RGBA 下游，公共交集为空，变更整体失败且既有分支帧号连续；显式 Tee+Convert 后成功。
- 确定性：变换下游连接声明顺序 100 次，协商契约一致。
