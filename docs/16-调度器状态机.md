## 2. Node 状态机

图：`diagrams/scheduler-node-state-machine.mmd`

```text
created ─Open─→ opening ─ok─→ ready ⇄ running ─┐
                    │                │  ▲      │ TryEnterDraining (in_flight==0)
                    │ error          │  │      ▼
                    ▼            EnterAsync  draining ─EOS 全送达─→ closing ─Close─→ closed
                  failed         Pending ⇄ async_pending      │
                                                              └─FLUSH error─→ failed
```

`NodeState` 是唯一的"主状态"，由 `NodeRuntime` 内的原子 CAS 守护；调度器不直接写状态，只调用 `TrySchedule / CancelSchedule / BeginInvoke / EndInvoke / TryEnterDraining / EnterClosing / Fail`。

### 2.1 正交标志

四个原子 bool 与主状态正交，组合出"同一个 ready 节点为什么这一轮不跑"的全部原因：

| 标志 | 谁置位 | 效果 | 谁清除 |
|---|---|---|---|
| `held` | `Publish` 对 removed 边的 kept 生产者 | `TrySchedule` 失败；InvokeBody 直接退出 | `Publish` 换拓扑后 `Release` + `MarkReady` |
| `retiring` | `Publish(Drain)` 对 removed 节点 | 源不再拉取，下一回合 `FinishNode`（flush+EOS） | 不清除（节点随后关闭） |
| `cancelled` | `ApplyFastLocked` / `Stop(fast)` | emit 被拒，返回错误不算失败；空闲时 `TryCloseCancelled` 立即关闭 | 不清除 |
| `busy` | `Invoke` 进入/退出 | `TryCloseCancelled` 跳过忙节点，由 `Invoke` 尾部自己关闭 | `ExitBusy` |

**不变量**：`cancelled` 节点只会在 `TryCloseCancelled` 或 `Invoke` 尾部被关闭，二者用 `TryEnterDraining` CAS 保证恰好一个关闭者。

### 2.2 调度槽位

- `TrySchedule` 占一个槽（单并行度 = ready CAS，N>1 = `available_slots--`），成功才提交执行器任务。
- 任务对象持有 `PendingGuard`：任务未运行就被执行器丢弃（Stop）时归还槽位并递减 `pending_tasks_`，析构函数以此等待所有任务出栈。
- `MarkReady` 在 `!started / fast_stop / !alive` 时直接返回：Fast 停止后不再有新回合。

## 3. Invoke 决策树

图：`diagrams/scheduler-invoke-decision.mmd`

一次执行器回合 = `Invoke(node)`，顺序检查以下门槛，任一命中即 `CancelSchedule` 归还槽位并退出；每个门槛都对应一个明确的"谁负责再次 MarkReady"：

| # | 门槛 | 退出后由谁唤醒 |
|---|---|---|
| 1 | state ∉ {ready, running} | 无（终态） |
| 2 | `fast_stop ∨ cancelled` | `Invoke` 尾部 `TryCloseCancelled` 关闭 |
| 3 | `held` | `Publish::Release` |
| 4 | 无拓扑快照 | 无（已 OnNodeDone） |
| 5 | 有停放包且 `RetryParked` 未清空 | 下游 `Pop → ClearBackpressure → RetryParked` |
| 6 | `OutputsBlocked`（block 边满） | 下游 `Pop → ClearBackpressure → MarkReady` |

门槛 5/6 有一处**丢失唤醒**窗口：下游 `Pop` 发生在本轮判定之后、`CancelSchedule` 之前时，它的 `MarkReady` 因槽位仍被占用而 `TrySchedule` 失败，此后无人再唤醒（`e0` 满、上游停放、下游空闲，全部静止）。因此 `CancelSchedule` 归还槽位后必须**重检一次**：停放已清空 / 输出不再阻塞且未 `held` → 自行 `MarkReady`。这与 `RunProcess` 空批路径的 `MayBeReady` 守卫是同一模式。回归用例：`SchedulerTest.SyncEmitOverrunIsParkedNotDroppedAndStaysOrdered`（仅在 CPU 争用下复现，超时后 dump 节点/边状态）。

通过后按节点类型分派：

- **RunSource**：`paused ∧ !retiring` 退出；`stopping ∨ retiring` → `FinishNode`；否则 `Process(input_count=0)`，`kExhausted` → `FinishNode`，`kContinue` 且输出未阻塞 → 自驱 `MarkReady`。
- **RunProcess**：`TryAcquire` 取批；先对每条输入边 `ClearBackpressure` 并唤醒上游（有停放则 `RetryParked`，draining 则 `RetryBlocked`，否则 `MarkReady`）；批为空且 `InputEnded` → `FinishNode`；否则 `SwitchAtPacketBoundary` 后 `Process`。
- **RunAsync**：在途达上限 → `ParkAsync`；批交给 `AsyncRuntime` 立即返回；输入结束但仍有在途 → `ParkAsync(until_zero)`，由 `OnAsyncIdle` 回来。

**失败路径**统一：`Fail` 先于 `EndInvoke`（不再准入），然后 `on_node_failed → OnNodeDone`；若节点已 `cancelled`，错误视为正常关闭。

### 3.1 FinishNode（12 §4.4 步骤 3–4）

前置：节点处于 draining，由观察到输入结束的那个线程调用。`TryEnterDraining` 要求 `in_flight==0` **且全部槽位空闲**（`available_slots == max_parallelism`）：N>1 的无状态节点上，兄弟任务可能已 `TryAcquire` 取走一批但尚未 `BeginInvoke`，仅看 `in_flight` 会让它在 EOS 之后再 Emit（包被下游丢弃）。CAS 进入 draining 后再复查一次槽位（与 `TrySchedule` 的 Dekker），失败则回退 ready。所有调用点在询问前先归还自己的槽位（`CancelSchedule`/`EndInvoke`）。

1. `Process(FLUSH)`，错误则 `Fail`；
2. 把全部输出端口登记到 `eos_retry_`；
3. `RetryBlocked`：先清空停放数据（EOS 不能越过数据，§4.2），再逐端口 `EmitEos`；`WOULD_BLOCK` 的端口留在表中，由下游 `Pop` 或 `Tick` 再试；
4. 全部送达 → `CloseNode → OnNodeDone`。

## 4. 背压与停放（12 §6.2）

block 策略的含义是"禁止继续生产"，不是阻塞线程。实现分两层：

### 4.1 生产前：OutputsBlocked

Invoke 前检查所有 block 边；任一 `full()` 则 `MarkBackpressured`（active→backpressured，若此刻已不满则撤销）并退出。下游 `Pop` 时 `ClearBackpressure` 成功即 `MarkReady` 上游。这是**主路径**：正常情况下节点不会在边满时被调用。

### 4.2 生产中：停放（Park）

同步 `Process` 内一次 emit 多包（或多路扇出），后面的包可能撞上刚被填满的边。此时 `Sink::Emit` 不返回错误，而是把 `(edge, packet)` 追加到 `parked_[node]`，**对算子而言 emit 已成功**（不重试、不丢）。

规则：
- 同边 FIFO：某边已有停放包时，后续发往该边的包直接停放，不越过；
- 有停放包的节点不再被调用（门槛 5），直到 `RetryParked` 清空；
- `RetryParked` 全局串行（`park_retry_mutex_`），重试期间新停放的包接在尾部；
- 节点 `cancelled` 或 `OnNodeDone` 时 `DropParked` 直接丢弃。

### 4.3 EOS 重试：RetryBlocked

`eos_retry_[node]` 记录 `EmitEos` 撞满的端口。调用时机：`FinishNode`、下游 `Pop` 发现上游 draining、`Tick` 对 retiring 节点、`TryCloseCancelled` 对 draining 节点。先 `RetryParked`（数据在前），全部端口送达后关闭节点。

### 4.4 三套机制的关系

```text
OutputsBlocked  ──主路径──  边满就不调用            唤醒: Pop→ClearBackpressure→MarkReady
Park/RetryParked ─兜底──  调用中撞满，数据停放     唤醒: Pop→ClearBackpressure→RetryParked
RetryBlocked    ─收尾──  EOS 撞满，端口登记        唤醒: Pop(上游 draining) / Tick
ParkAsync       ─异步──  在途达上限，节点挂起      唤醒: EndAsync→OnAsyncIdle→MarkReady
```

顺序保证：同一条边上 `停放数据 → EOS`，因为 `RetryBlocked` 总是先 `RetryParked`。

## 5. Publish 与 Retire（12 §7.2 B1–B5、§7.7）

图：`diagrams/scheduler-retire-state-machine.mmd`

### 5.1 Publish

1. 分类 Vn 的节点/边为 kept / removed；
2. removed 边的 **kept 生产者** `Hold` 并 `WaitQuiescent`（最多等一次在途调用，MUT-3）；
3. **B1 换拓扑**（持 `swap_mutex_`）：再查一次 `stopping_`——为真则 `Release` 被 hold 的节点并返回 `kCancelled`（协调器 `AbandonCandidate`）；否则 `ApplyRebinds`，Vn+1 所有节点 `SetTopology(next)`，原子替换 `topology_`，`AttachNodes(new_nodes)`；removed 节点继续持有 Vn。`Stop` 的 `LiveNodes` 快照 + 置 `stopping_` 也在同一把锁内，所以新节点要么进入 Stop 的扫描集合，要么根本不被发布——没有"发布了但无人关闭"的第三种结果（Linux TSan stress 首跑暴露：`DrainStopWithPendingMutations` 的 `sink_q0` 永不 closed、Stop 操作 10s 不终止）；
4. **B3**：Drain 策略下 removed 节点 `MarkRetiring`；kept 生产者的 removed 边 `MarkDraining` 并排队一个 EOS 标记（`pending_inject_`）；生产者也被删除的边不注入，等生产者自己的 EOS；Fast 策略直接 `ApplyFastLocked`；
5. `RetryInjections`、`Release` 被 hold 的节点、对 Vn+1 所有可运行节点与 removed 节点各 `MarkReady` 一次、`Tick`。

### 5.2 Retired 条目状态

| 状态 | 进入 | 离开 |
|---|---|---|
| Draining | Publish(Drain) | `DrainComplete` → Completed；超时 / `Stop(fast)` → FastApplied |
| FastApplied | Publish(Fast) / 超时 / Stop(fast) | removed 节点全部 closed/failed → Completed |
| Completed | — | `on_complete(timed_out)`，条目移除 |

`DrainComplete` 的判定：removed 节点全部终态；removed 边要么已 retired，要么"队列空 ∧ 无待注入 ∧ 其 removed 一端已终态"。

### 5.3 Tick（看门狗）

任意线程可调，空闲时 O(1)：`RetryInjections` → 若无 retired 条目返回 → 对每个 removed 节点按状态推一把（draining → `RetryBlocked`；ready/running 且 cancelled → `TryCloseCancelled`；否则 `MarkReady`）→ 循环 `CompleteRetired` 直到无进展。

触发点：会话看门狗线程 / 宿主 `Engine::Tick`、`Publish` 末尾、`RunProcess/RunAsync` 的 Pop 后（`retire_pending_ != 0` 时）、`OnNodeDone`。

## 6. 锁与线程

| 锁 | 保护 | 持锁期间禁止 |
|---|---|---|
| `live_mutex_` | `live_nodes_` | 调 `MarkReady`（会 `SubmitCpu`，无死锁风险但避免） |
| `park_mutex_` | `parked_` | 推包（`PushOne` 在锁外） |
| `park_retry_mutex_` | 同一时刻只有一个 `RetryParked` 遍历 | — |
| `retry_mutex_` | `eos_retry_` | `MarkReady`（唤醒列表在锁外处理） |
| `retire_mutex_` | `retired_`、`pending_inject_` | `TryCloseCancelled`、`on_complete`（收集后锁外调用） |
| `closed_mutex_` | `closed_signalled_`、`pending_tasks_` 等待 | — |
| `swap_mutex_` | `Publish` 的 stopping 检查→`AttachNodes` 与 `Stop` 的 `LiveNodes` 快照→置 `stopping_` 互斥 | `MarkReady`、`Tick`（都在锁外） |

`pending_tasks_` 的递减必须在 `closed_mutex_` 内：`~Scheduler` 用它做谓词等待，锁外递减 + 锁内 notify 的窗口里析构可能已完成，随后的 `lock` 命中已销毁的 mutex（`mutex lock failed: EINVAL`）。同样约束适用于 `Session::OnAllClosed`：它在执行器线程上跑，`Operation::Succeed` 一旦唤醒宿主，`Session` 可能立即析构（`~Scheduler` 等的是本任务，但 `stop_mutex_` 声明在 `scheduler_` 之后、先被销毁），所以状态迁移、`stopped_signalled_`、`notify` 都在一次持锁内完成，`Succeed` 放最后且不再触碰 `this`。

回调线程约定：`on_node_failed`、`on_operator_event` 在执行器线程；`on_all_closed` 在最后一个节点关闭的线程；`on_drain_timeout`、`RetireRequest::on_complete` 在调用 `Tick` 的线程（看门狗或执行器）。

## 7. 已知边界

- `Stop(fast)` 先 `MarkCancelled` 再置 `stopping_`：源节点若先看到 `stopping_` 会走 drain 路径（EOS + 非 fast `Close`），下游收到的就不是 `fast_shutdown`。
- `RunProcessCall` 在 `EndInvoke` **之前** `req.inputs.clear()`：槽位一旦归还，另一执行器线程可能立刻 drain 并关闭本节点、sink 乃至发出 all-closed；此时本帧还持有输入包的 `PacketRef`，Stop 后紧接的 `live_buffers == 0` 检查就会看到 1（TSan stress `ConsecutiveInsertsNeverHalfInserted`）。
- `RunProcess` 在 `Process` 返回后立即释放批中的 `PacketRef`（`req.inputs.clear()`），否则 `FinishNode → OnNodeDone → on_all_closed` 唤醒宿主时，宿主的泄漏检查会看到仍被栈上 `req` 持有的 buffer。
- `Park` 只在边仍属于节点当前拓扑时停放；换拓扑后撞满的旧边包被丢弃（生产者已被 hold 并等待静默，正常不会发生）。
- `WaitQuiescent` 在内联执行器上会代跑任务（`RunOne`），因此 `Publish` 不得在执行器线程上调用。
- 异步节点单槽位（提交顺序 = seq 顺序）；`ParkAsync` 与 `EndAsync` 之间是 Dekker 式再检查，见 `NodeRuntime::TryLeaveAsyncPending`。
- **Session 生命周期与两条后台线程（Linux CI 首跑发现，macOS 从未复现）**：
  - `Engine::sessions_` 持 `shared_ptr<Session>`。`Engine::Tick`/`StopAll` 在 `sessions_mutex_` 外调用 `Session::Tick`，快照必须持引用，否则并发 `DestroySession` 释放的是看门狗正在 tick 的对象。代价：`DestroySession` 在 `reset()` 后要等 `weak_ptr` 过期（1ms 轮询、5s 上限）再 `CompletePendingUnloads`，因为插件租约在 `~Session` 归还，早一步会看到 `references remain`。
  - `AsyncRuntime` 的 session hooks（`after_emit`/`on_async_idle`/`on_node_failed`）捕获 `Session*`，在消费线程上、`state_mutex_` 外调用。`SessionEntry::guard`（`shared_mutex` + `alive`）让每次调用持 shared lock，`DetachSession` 最后取 exclusive lock 置 `alive=false`——它返回时保证没有 hook 还在 `Session` 内。hook 不回调 `DetachSession`，无自死锁。典型触发链：`OnCompletion → on_node_failed → Session::OnNodeFailed → Scheduler::Stop(fast)`，同时宿主 `WaitStopped` 返回后立刻析构。
