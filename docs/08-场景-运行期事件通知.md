# 场景需求分析：图执行期事件与格式变化通知

> 依据 `docs/01-需求分析.md` FR-RT-6/7、FR-SC-7。本文档只做需求分析，不涉及设计。

## 1. 场景背景

图运行中，节点会遇到影响数据处理但不必改变图拓扑的事件。例如解码器从码流中发现分辨率、像素格式或帧率发生变化；拉流节点发生重连、EOS 或丢帧。

事件需要服务两个独立目的：

1. **数据面协同**：受影响的下游节点在正确的帧边界切换处理能力，避免新旧格式混用、花屏或错误编码。
2. **上层可观测**：业务/运维获知发生了什么，用于告警、审计与后续策略；上层在本期仅观察，不介入处理决策，也不阻塞数据面。

## 2. 已确认口径

| 维度 | 决策 | 需求含义 |
|---|---|---|
| 上层通知 | **仅观察告警** | 图引擎向订阅者上报事件；上层不能确认、拒绝或阻塞事件处理，不参与数据面时序 |
| 格式事件数据面方向 | **向下游传播** | 解码节点发现分辨率变化后，格式事件与触发变化的关键帧绑定，沿受影响下游路径传播 |
| 节点响应 | **节点声明能力** | 节点声明支持哪些格式变化；收到事件后确认处理、拒绝处理或报告需要重建。引擎记录结果并按策略处理 |
| 生效边界 | **与关键帧绑定** | 从携带新格式的关键帧开始，受影响路径必须以完整新格式处理；关键帧之前的帧保持旧格式语义 |
| 第一期开通范围 | **媒体格式事件、运行状态事件、上游控制事件** | AI/设备事件暂不纳入本场景第一期 |

## 3. 事件分类

| 类别 | 事件示例 | 传播/上报 |
|---|---|---|
| 媒体格式事件 | 分辨率、像素格式、帧率、色彩空间、HDR 参数变化 | 下游数据面传播 + 上层观察告警 |
| 运行状态事件 | EOS、解码错误、拉流重连、卡顿、丢帧、时钟跳变 | 上层观察告警；按节点声明可沿路径传播状态 |
| 上游控制事件 | 请求关键帧、请求源端降码率、选择清晰度、请求重连 | 由节点向上游路径传递；上层仅观察 |

## 4. 用户故事

- **US-E1** 作为业务运维，当解码器检测到输入从 1920×1080 变为 1280×720 时，我收到包含会话、节点、旧新格式、触发 PTS/关键帧序号的观察事件；该告警不阻塞视频继续处理。
- **US-E2** 作为下游缩放/合成/编码算子开发者，我声明自己支持哪些格式变化；当事件与关键帧到达时，能在处理该帧前完成格式切换。
- **US-E3** 作为业务方，当下游节点不支持新格式时，图引擎上报明确失败事件及受影响路径；其他未受影响分支继续运行。
- **US-E4** 作为拉流策略系统，当下游检测到需要关键帧时，节点可发起上游控制事件请求关键帧；上层同时收到观察记录，但不参与请求确认。
- **US-E5** 作为运维，我查询事件历史，能关联格式变化前后帧号、节点处理结果与最终会话状态。

## 5. 功能需求

### 5.1 事件通用契约

| 编号 | 需求 | 优先级 |
|---|---|---|
| EV-C-1 | 事件必须包含：事件 ID、类别、事件类型、会话/图 ID、源节点、发生时间、关联 Packet 序号/PTS（如有）、严重级别、结构化详情 | P0 |
| EV-C-2 | 事件区分数据面事件与观察事件：数据面事件用于节点协同；观察事件为数据面事件的不可阻塞副本，投递给上层订阅者 | P0 |
| EV-C-3 | 观察事件投递失败、超时或订阅者处理缓慢不得阻塞、重试或影响数据面 | P0 |
| EV-C-4 | 事件支持去重/合并：同一节点短时间连续报告相同格式或相同状态时，可合并计数并保留首次/最后一次时间 | P1 |
| EV-C-5 | 所有事件写入结构化日志与指标；观察订阅可按图、会话、节点、事件类型过滤 | P1 |

### 5.2 媒体格式变化事件

| 编号 | 需求 | 优先级 |
|---|---|---|
| EV-M-1 | 解码/媒体 Source 节点检测到分辨率、像素格式、帧率、色彩空间、HDR 元数据变化时，生成 `MediaFormatChanged` 事件 | P0 |
| EV-M-2 | 事件详情包含完整旧/新格式描述：宽高、像素格式、帧率、色彩空间、色彩范围、HDR 参数及 codec 参数变化（如可得） | P0 |
| EV-M-3 | 格式事件必须与触发新格式的**关键帧**绑定，包含该关键帧的 Packet 序号与 PTS | P0 |
| EV-M-4 | 从绑定关键帧开始，格式事件先于该帧抵达受影响的下游节点；关键帧前的 Packet 继续用旧格式处理 | P0 |
| EV-M-5 | 下游 Node 在元数据中声明其支持的格式变化能力；收到事件后可返回：已处理 / 不支持 / 需要重建 / 失败 | P0 |
| EV-M-6 | 关键路径上任一 Node 返回不支持、需要重建或失败时，引擎上报事件及受影响路径；本期不等待上层确认 | P0 |
| EV-M-7 | 未受影响的分支（如独立音频分支、未连接该视频输出的分支）不得因格式事件暂停或丢帧 | P0 |
| EV-M-8 | 格式变化处理结果与实际生效 Packet 序号/PTS 形成审计记录 | P1 |

### 5.3 运行状态事件

| 编号 | 需求 | 优先级 |
|---|---|---|
| EV-R-1 | 节点支持上报：EOS、错误、拉流连接/重连、卡顿、丢帧、时钟跳变等状态事件 | P0 |
| EV-R-2 | 错误事件必须附带错误码、可读原因、可重试性、影响范围（节点/分支/会话） | P0 |
| EV-R-3 | 事件与既有错误策略（FR-RT-6）关联：图级致命/节点重启/忽略计数等处理由图配置决定；上层仅观察最终结果 | P0 |
| EV-R-4 | EOS 在数据面沿边传播，同时向上层产生观察事件；观察事件不得改变 EOS 的传播/关闭时序 | P0 |

### 5.4 上游控制事件

| 编号 | 需求 | 优先级 |
|---|---|---|
| EV-U-1 | 节点可向上游路径发送控制事件：请求关键帧、请求源端降码率、选择清晰度、请求重连 | P1 |
| EV-U-2 | 上游节点在元数据中声明支持的控制事件；不支持时返回拒绝/忽略结果并上报观察事件 | P1 |
| EV-U-3 | 上游控制事件必须包含目标范围与原因，避免广播到不相关输入分支 | P1 |
| EV-U-4 | 控制事件的成功/拒绝/超时均生成观察事件；上层不参与确认和重试 | P1 |

### 5.5 上层观察接口

| 编号 | 需求 | 优先级 |
|---|---|---|
| EV-O-1 | 提供事件订阅 API：按图、会话、节点、类型、严重级别订阅观察事件 | P0 |
| EV-O-2 | 订阅接口为单向只读：订阅者不能通过事件回调阻塞、确认、拒绝或修改图处理 | P0 |
| EV-O-3 | 提供事件历史查询：支持按时间范围、事件 ID、会话、节点检索，并关联格式处理结果 | P1 |
| EV-O-4 | 指标至少包括：按类型事件总数、合并数、格式变化成功/失败数、观察投递丢弃数 | P1 |

## 6. 一致性与失败语义

- 格式变化的唯一数据面切换点是绑定关键帧；禁止独立异步通知导致部分节点先处理新格式、部分仍以旧格式处理。
- 上层观察事件属于旁路，任何观察路径的故障不影响格式事件传播、关键帧处理或节点响应。
- 本期上层不能主动确认/拒绝格式事件；当节点返回"需要重建"时，引擎仅告警和记录，后续图变更由外部系统在独立控制流程中发起。
- 同一流连续多次格式变化时，必须按关键帧序号顺序处理与上报；不得倒序覆盖。

## 7. 非功能需求

| 编号 | 指标 | 目标 |
|---|---|---|
| EN-1 | 格式事件生成到受影响下游节点可见 | < 1 个 Packet 周期 |
| EN-2 | 观察事件投递对数据面额外开销 | < 5 µs/事件，且不得引入数据面阻塞 |
| EN-3 | 格式变化期间未受影响分支 | 0 丢帧、无额外暂停 |
| EN-4 | 事件历史查询 | 近 24h 内按会话查询 < 100ms |

## 8. 验收要点

- 输入流在关键帧处从 1080p 切换至 720p：下游先收到格式事件再处理关键帧；旧帧按旧格式、新帧按新格式，无花屏。
- 人为让某下游节点不支持新像素格式：图产生包含受影响路径的告警；其他无关分支帧号连续。
- 停止/阻塞上层订阅者：确认视频数据面仍按原帧率运行，观察投递丢弃数可见。
- Source 发生重连、EOS、请求关键帧：观察事件完整记录；上游控制事件不支持时产生拒绝事件但不影响会话。
