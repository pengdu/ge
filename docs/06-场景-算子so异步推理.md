# 场景需求分析：算子 so 的异步推理

> 依据 `docs/01-需求分析.md`（FR-SC-4/8、FR-OP-4）与 `docs/05-场景-算子so集成.md`。本文档只做需求分析，不涉及设计。

## 1. 场景背景

推理类算子（检测/分割/生成式特效）是流水线中最重的环节，单帧推理耗时 5-50ms。若算子以**同步接口**运行：

- 节点执行被推理阻塞：Executor 线程提交推理后空等，线程利用率低
- GPU 与 CPU 阶段（前处理、后处理、编码）无法重叠，端到端延迟被拉长为各段之和
- 跨会话合批（FR-SC-4）在同步模型下无解：等待凑批期间线程被占满，凑批越多占线程越多

因此推理算子 so 必须支持**异步接口**：提交推理立即返回，完成后结果异步送达，让 GPU 计算、CPU 处理、多请求合批在时间上重叠。

### 1.1 已确认口径

| 问题 | 结论 | 对需求的影响 |
|---|---|---|
| 异步完成驱动 | **引擎驱动完成**：算子 so **不允许自建线程**。Submit 提交推理立即返回；完成后由引擎提供的机制（完成后回调/事件通道）触发结果交付。推理后端（TensorRT/ORT）自身的回调能力被引导接入引擎通道 | so 的异步能力契约 = 纯提交 + 回调；卸载安全性最好（无遗留线程问题，直接关闭 05-Q5）；引擎必须定义回调注册/完成分发协议作为算子接口的一部分 |
| 与合批的关系 | **异步接口与跨会话合批绑定**：合批等待期间不占线程，batch 就绪后一次 Submit；合批是异步推理的首要受益场景 | 合批（FR-SC-4）与异步算子接口作为一组需求绑定验收：场景 C（多路摄像头分析）成为本场景的主验收场景 |

## 2. 与既有需求的关系

| 依赖 | 内容 | 本场景的强化 |
|---|---|---|
| FR-SC-4 跨会话合批 | 多会话同类型推理节点合并 batch | 同步模型下合批不可实现，本需求是 FR-SC-4 的**前置条件** |
| FR-SC-8 GPU 流水线 | CUDA Stream 级异步、零拷贝 | 异步推理是 GPU 流水线的一环：前处理 Stream → 推理 → 后处理 Stream 全链重叠 |
| FR-DM 节点并行 | parallelism>1、输出保序 | 异步节点在途请求可多个，输出保序从"完成即发"变为"完成回调后仍需按序号对齐再发" |
| 05 文档 PL-D-4 | so 卸载安全：无遗留线程 | 引擎驱动完成使异步推理 so 天然满足；推理后端的内部线程（如 TRT 执行流）归属 Close 时销毁的引擎侧资源 |
| FR-OP-4 推理算子 | 多模型实例、动态 batch | 模型实例池在异步下才可被多请求真正并发复用 |

## 3. 用户故事

- **US-AS1** 作为推理算子开发者（so），我不需要管理任何线程：Submit 一个或多个推理请求立即返回，完成后调用引擎提供的完成通道，请求间的并行与重叠由引擎与后端完成。
- **US-AS2** 作为推理算子开发者，我的模型最大 batch=8、单请求 batch=1 也接受：引擎（或上层 Batcher 语义）决定怎么凑批，我只看到 batch 请求。
- **US-AS3** 作为业务方，同型号 GPU 上多路会话共享推理时，合批让单卡路数显著高于逐路独立推理（目标值见 §6）。
- **US-AS4** 作为业务方，实时会话的推理请求在 ≤ N ms（可配 batch 超时）内必被提交，不为凑批无限等待；合批策略可按会话/节点关闭。
- **US-AS5** 作为业务方，异步推理失败（模型错、显存不足、后端错误）时，只影响该请求对应的帧与会话的降级策略，不影响其他在途请求。
- **US-AS6** 作为运维，我要看到每个推理实例的在途请求数、batch 分布、等待凑批时长、完成延迟分布，用于定位"凑批过度导致延迟"或"batch 不饱和导致吞吐低"。
- **US-AS7** 作为业务方，图停止/变更（含模型热更新、算子版本升级）时，在途请求被有序收尾：已提交的推理要么完成并交付、要么取消并丢弃对应帧，不产生孤儿结果延迟返回到已变更的图。

## 4. 功能需求

### 4.1 异步算子接口（so 契约）

| 编号 | 需求 | 优先级 |
|---|---|---|
| AS-I-1 | 推理类算子 so 实现异步契约：`Submit(请求) → 句柄`，立即返回不阻塞；请求携带输入（Buffer/引用）、回调目标、序号 | P0 |
| AS-I-2 | **算子 so 内禁止创建/持有工作线程**（复用 05-Q5 决策）：异步性完全通过引擎提供的"完成通知通道"实现；后端原生回调（TRT enqueueV3、ORT RunAsync）由 so 转接到该通道 | P0 |
| AS-I-3 | 引擎向 so 提供**完成事件队列**（Completion Queue）：so 完成后仅投递事件，引擎专用上下文消费并分发；so 不得直接调用图回调、不得自建完成分发线程。事件必须携带请求句柄、原始序号、结果/错误、拓扑版本标识 | P0 |
| AS-I-4 | 请求/句柄生命周期：句柄在完成或取消前有效；so 不持有请求输入 Buffer 的所有权之外引用；完成后释放（复用 Buffer 引用计数） | P0 |
| AS-I-5 | 同步算子接口保留（非推理算子、简单 CPU 算子仍为同步 Process），接口类型由算子元数据声明，图校验时检查端口语义匹配 | P0 |
| AS-I-6 | 算子可声明并发容量（最大在途请求数），引擎限流保护，超出排队于引擎侧而非 so 内部 | P1 |

### 4.2 结果交付与保序

| 编号 | 需求 | 优先级 |
|---|---|---|
| AS-D-1 | 完成回调携带结果与原请求序号；多路并发（parallelism>1 或多请求在途）时，节点输出仍按输入序号保序交付下游 | P0 |
| AS-D-2 | 保序不牺牲吞吐：乱序完成的请求在 reorder 缓冲中对齐；头阻塞超时后**允许放行已有前缀并产生序号缺口**，缺失请求必须带 `dropped/timeout` 元数据标记（不可静默省略），下游据此容错 | P0 |
| AS-D-3 | 推理结果帧与请求输入帧的元数据（时间戳/序列号/自定义 meta）完整透传，下游可关联原始帧（如检测框叠回原视频帧） | P0 |

### 4.3 跨会话合批（绑定验收）

| 编号 | 需求 | 优先级 |
|---|---|---|
| AS-B-1 | 同一算子类型 + 同一模型配置 + **同一 device_id** 的跨会话请求可合批；**仅同卡合批，禁止跨 GPU 搬运聚合**。batch 上限（模型支持值）、超时上限（**默认 10ms**，可配）双约束，先到先满足 | P0 |
| AS-B-2 | 凑批期间不占用任何 Executor 线程；batch 就绪后单次 Submit | P0 |
| AS-B-3 | 合批粒度可配：按会话关闭（实时单路）、按节点关闭、全局关闭 | P0 |
| AS-B-4 | 合批结果按请求来源拆分，分别送回各自会话的输出边，互不串扰（含元数据对应关系） | P0 |
| AS-B-5 | 合批与模型实例池协同：batch 数量超过单实例容量时可并行多实例 Submit 或排队（策略可配） | P1 |
| AS-B-6 | 合批错误隔离：batch 内单请求导致的整批失败时，错误只归属到可判定的请求，其余请求不因整批重试被重复处理（后端行为决定是否可部分成功，需在算子元数据声明） | P1 |

### 4.4 生命周期协同（与图变更/so 卸载）

| 编号 | 需求 | 优先级 |
|---|---|---|
| AS-L-1 | 图 Stop/Flush：**首期不提供 Cancel**，等待在途请求完成；等待超时后丢弃结果，之后算子 Close。Close 后不得再有完成事件进入图；模型/后端元数据必须声明最大推理时长，作为等待超时配置依据 | P0 |
| AS-L-2 | 模型热更新/算子版本升级（图变更事务）：切换后新请求进新版本，旧版本的在途请求按 AS-L-1 收尾，结果不得注入已切换的新拓扑（孤儿结果） | P0 |
| AS-L-3 | so 卸载前置检查包含：该 so 的全部推理实例在途请求为零（复用 PL-D-1/4） | P0 |
| AS-L-4 | 会话销毁时其合批槽位立即退出，不影响同批其他会话 | P0 |

### 4.5 观测

| 编号 | 需求 | 优先级 |
|---|---|---|
| AS-O-1 | 指标：每推理实例在途数、batch 大小分布、凑批等待时长分布、端到端完成延迟（P50/P99）、超时凑批占比、取消/失败数 | P0 |
| AS-O-2 | 指标可回答两个典型诊断："凑批过度导致延迟上升"（超时凑批占比高）与"batch 不饱和导致吞吐低"（batch 分布偏小） | P0 |

## 5. 非功能需求

| 编号 | 指标 | 目标 |
|---|---|---|
| AN-1 | Submit 提交开销（引擎侧，不含推理本身） | < 5 µs |
| AN-2 | 完成回调到输出边可见 | < 10 µs |
| AN-3 | 异步化后 GPU 段重叠收益：推理 + 前后处理流水线 vs 同步版本 | 端到端吞吐提升 ≥ 2×（推理耗时占比 30% 以上场景） |
| AN-4 | 合批收益（场景 C，T4 级卡，检测模型，batch 上限 8） | 单卡路数较逐路独立推理 ≥ 3×，且单路端到端延迟 P99 增幅 ≤ 合批超时 + 1 帧周期 |
| AN-5 | 保序代价 | reorder 引入的额外延迟 ≤ 在途请求完成时间差（无额外固定开销） |
| AN-6 | 实时会话保护 | 关闭合批的会话延迟与无合批单路推理持平 |

## 6. 约束

- 异步契约限定于**推理/加速器类**算子；CPU 密集算子的并行仍走 parallelism + Executor 池，不强行异步化（避免接口复杂化）
- 完成通道的线程上下文由引擎定义（大概率是 Executor 工作线程或专用完成分发上下文），算子不得假设回调线程身份——这条属于算子开发规范的可校验部分
- so 内禁止线程的约束由 ABI 元数据声明 + 卸载前检查执行；违规定级为算子缺陷（非引擎责任），但引擎提供加载期自检辅助（探测 so 是否注册了线程构造活动属实现手段，不承诺检出率）

## 7. 开放问题（已全部决策）

| # | 问题 | 决策 | 落地 |
|---|---|---|---|
| Q1 | 完成通道形态 | **事件队列**：so 将完成事件投递至引擎 Completion Queue，由引擎专用上下文消费并分发；不允许 so 直接调用图回调 | AS-I-3 契约冻结；多一跳仅 µs 级，换取线程归属与卸载安全 |
| Q2 | 合批超时默认值 | **默认 10ms**，允许节点/模型覆盖配置 | AS-B-1、AN-4 的默认延迟预算确定 |
| Q3 | 合批是否跨 GPU | **仅同卡合批**，跨卡不聚合、不搬运输入 | AS-B-1 聚合键必须含 device_id |
| Q4 | reorder 超时序号缺口 | **允许缺口**：超时后可放行已有前缀，缺失请求以元数据标记；下游需具备缺口容错 | AS-D-2 吞吐优先语义确定 |
| Q5 | 在途请求取消 | **首期不提供 Cancel**：Stop/Flush/变更时等待在途完成；超时后丢弃结果且不得注入新图 | AS-L 收尾上界 = 可配等待超时 + 后端最长在途耗时 |

### 7.1 决策补充说明

- 事件队列将后端完成线程与图运行时隔离：so 只投递完成事件，不进入图对象；引擎消费事件时再做拓扑版本、会话状态、请求序号校验，天然阻断旧图的孤儿结果。
- 10ms 是默认折中值；实时会话必须显式覆盖为更小值，或关闭合批（AS-B-3）。
- 允许序号缺口时，完成事件必须含 `dropped/timeout` 标记与原始序号；不能静默省略，保证下游可观测、可容错。
- 无 Cancel 的前提下，模型/后端必须在元数据中声明最大推理时长，作为 Stop、热更新与 so 卸载的等待超时配置依据。

## 8. 验收要点

- 接口契约：同步/异步算子混布一图；异步算子 Submit 后节点立即可处理后续帧（在途并发数 > 1 可观测）
- 保序：单会话乱序注入（人为让后提交的请求先完成），输出序号连续或按 AS-D-2 策略处理且指标可见
- 合批：N 会话共流，观测 batch 分布与凑批等待；关闭某会话合批后其延迟恢复单路水平（AN-6）
- 吞吐：AN-3/AN-4 对比测试（同步版 vs 异步版、逐路 vs 合批）
- 生命周期：Stop/Flush/模型热更新/so 卸载各场景下无孤儿结果（变更后图不出现旧拓扑的迟到帧）、无完成回调晚于 Close（USE_AS7）
- 隔离：单请求失败不影响同批其他会话的结果正确性
