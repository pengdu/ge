# 场景需求分析：算子以独立 so 集成

> 依据 `docs/01-需求分析.md` FR-OP-1/5/6。本文档只做需求分析，不涉及设计。

## 1. 场景背景

第三方/跨团队开发的算子（编解码变体、特效、自研推理前后处理等）以独立共享库（.so）形式交付，不参与引擎主构建。引擎按需发现、加载、调用、并在必要时卸载这些算子 so。

### 1.1 已确认口径

| 问题 | 结论 | 对需求的影响 |
|---|---|---|
| 加载/卸载时机 | **可加载、可卸载、支持算子级热升级**：运行中加载新 so、卸载旧 so，能力最强但难度最高 | 需求上必须把"卸载安全性"（引用归零、静默期、延迟回收）定义为硬性要求；so 升级与图变更事务（FR-DM）需要语义协同 |
| ABI 边界 | **C++ ABI 同构建**：so 与引擎同编译器/同标准库/同编译选项，类接口直集成 | 需要强 ABI 版本检查：不匹配的 so 拒绝加载并给出明确错误；构建矩阵作为交付约束 |
| 多版本 | **多版本共存**：`type@version` 注册，图配置/变更可指定版本 | 支持灰度（新版本只给指定会话用）与回滚（改图指向旧版本）；版本选择语义进入配置格式与变更 API |
| 安全约束 | **白名单目录 + so 内元数据校验**；签名校验为 P2 | 加载入口封闭（仅扫描配置目录），元数据（ABI 版本、算子清单、依赖声明）不匹配即拒绝 |

### 1.2 关键张力（需求层面必须正视）

**C++ ABI 同构建 + 可卸载热升级** 是一组有内在冲突的决策：

- so 与引擎共享 C++ 运行时对象（STL 跨边界传递、异常跨 so 抛出、虚表跨 so 调用）时，`dlclose` 的安全性没有通用保证——卸载后任何残留引用（线程本地存储、静态析构顺序、跨 so 的对象生命周期）都可能导致崩溃
- 因此需求必须**以"可安全卸载"为验收目标倒推约束**：要么限制卸载语义（见 PL-D 组），要么接受"卸载 = 延迟/永不真正 dlclose"的降级，这必须在需求阶段明确，而不是留给实现阶段踩坑

## 2. 用户故事

- **US-P1** 作为算子开发者，我交付一个 so 文件（或 so + 模型资源包），放入约定目录并通知引擎后，它立即可用于新建图与运行中图的变更，无需重启引擎。
- **US-P2** 作为算子开发者，我发布 `beauty@2.0` 时，线上运行 `beauty@1.0` 的图不受影响；我将指定会话变更到 2.0 灰度验证，出问题可改回 1.0。
- **US-P3** 作为运维，我升级完成后下发"卸载旧版本"指令，引擎在确认无任何图引用后真正卸载并回收 so 占用的资源，返回确认。
- **US-P4** 作为运维，我加载一个与当前引擎 ABI 不匹配的 so（引擎升级后遗留的旧包），引擎拒绝加载并明确告知 ABI 版本不匹配及期望版本，不崩溃、不影响已加载算子。
- **US-P5** 作为算子开发者，我的 so 依赖第三方库（如 libavcodec 特定版本），我在元数据中声明；引擎加载前检查依赖可用性，避免运行时隐式冲突。
- **US-P6** 作为业务方，我加载的算子 so 存在缺陷导致崩溃时，影响范围可配置（拒绝加载/隔离），不得拖垮整个引擎进程与其他会话。
- **US-P7** 作为算子开发者，我需要官方的算子开发脚手架：头文件、构建配置模板（保证 ABI 一致）、元数据打包工具、以及 CI 中与引擎 ABI 自动对拍的检查。

## 4. 功能需求

### 4.1 发现与加载

| 编号 | 需求 | 优先级 |
|---|---|---|
| PL-A-1 | 引擎扫描配置指定的白名单目录（可多个）中的 so，按需加载：启动时全量 / 运行中增量（目录通知或显式 API） | P0 |
| PL-A-2 | 每个 so 内嵌元数据（嵌入符号或伴生清单文件，二选一由规范定）：算子清单（type、版本、能力声明）、引擎 ABI 版本、依赖声明（库/版本/硬件）、构建指纹 | P0 |
| PL-A-3 | 加载前校验链：ABI 版本匹配 → 依赖可用 → 元数据与符号完整性（注册函数可解析）；任一失败拒绝加载，返回结构化错误（含原因与期望值） | P0 |
| PL-A-4 | 加载 so 中声明的全部算子注册进全局注册表；类型+版本冲突（同 type@version 已存在）拒绝注册并指明来源 so | P0 |
| PL-A-5 | 部分失败隔离：so 中 10 个算子 1 个注册失败时策略可配（整包拒绝 / 跳过该算子加载其余），默认整包拒绝 | P1 |
| PL-A-6 | 运行中加载的 so 立即可用于：新建图、运行中图的变更事务（作为 AddNode 的类型来源） | P0 |

### 4.2 版本与选择

| 编号 | 需求 | 优先级 |
|---|---|---|
| PL-V-1 | 同一算子类型允许多版本 so 共存注册（`beauty@1.0` / `beauty@2.0`），可来自不同 so | P0 |
| PL-V-2 | 图配置与变更 API 中指定算子版本；未指定时按解析规则（默认最新 / 引擎配置固定版本）并可全局禁用"默认最新"（生产环境要求显式版本） | P0 |
| PL-V-3 | 运行中的图变更（节点替换/子图变更）可切换算子版本，复用图变更事务语义：预热新版本节点 → 原子切换 → 旧版本节点排空销毁 | P0 |
| PL-V-4 | 灰度支持：仅指定会话切新版本（会话级变更天然满足）；提供查询"各版本当前被哪些图/节点引用" | P1 |
| PL-V-5 | 算子版本不影响端口类型契约：同类型不同版本的输入输出端口兼容性由算子元数据声明，校验器加载时校验跨版本兼容矩阵 | P1 |

### 4.3 卸载与热升级

| 编号 | 需求 | 优先级 |
|---|---|---|
| PL-D-1 | 卸载前置条件：目标 so（或版本）不被任何运行图引用；引擎返回当前引用清单，引用非零时拒绝卸载或按策略等待 | P0 |
| PL-D-2 | 卸载执行语义：先使注册表中该版本不可再被引用（新图/变更拒绝），再等待存量引用随图停止/变更自然归零，最后真正卸载 | P0 |
| PL-D-3 | **强制卸载**（升级收尾用）：对仍被引用的版本，可选择"拒绝"或"联动变更"（由调用方先做图变更再卸载，引擎提供一键辅助：把引用节点替换为指定新版本）；引擎不得主动卸载仍被引用的 so | P0 |
| PL-D-4 | 卸载安全性硬性要求：卸载后不得出现延迟崩溃——so 内不得遗留：运行中线程、未到期定时器、静态对象析构后仍被访问的注册回调、跨 so 传递且未释放的堆对象；由算子开发规范 + 引擎卸载前静默检查（引用计数、线程存活探测）双重保证 | P0 |
| PL-D-5 | 卸载降级：无法证明安全 dlclose 时（ABI/静态析构风险），允许引擎降级为"逻辑卸载"（从注册表移除、资源释放、句柄保留），并将降级事件上报；逻辑卸载后重载同版本 so 必须仍可用 | P1 |
| PL-D-6 | 热升级完整流程：加载新版 so → 灰度切换会话 → 收尾卸载旧版，全程引擎与既有图不重启 | P0 |

### 4.4 稳定性与安全

| 编号 | 需求 | 优先级 |
|---|---|---|
| PL-S-1 | so 内注册函数执行在受控上下文中：加载过程崩溃/超时（可配）不拖垮引擎，标记 so 为损坏并隔离 | P0 |
| PL-S-2 | 算子运行期崩溃按 FR-RT-6 既有策略（节点级捕获）；so 级缺陷高发时可标记整个 so 隔离（其算子不再可新建） | P1 |
| PL-S-3 | 白名单目录之外不加载；符号解析失败、依赖缺失、ABI 不匹配的 so 全部拒绝且不影响其他 so | P0 |
| PL-S-4 | so 包签名校验（发布链路完整时启用） | P2 |
| PL-S-5 | 审计：so 的加载/注册/版本引用/卸载全过程产生事件日志，可回答"某时刻某会话用的哪个 so 的哪个版本" | P0 |

### 4.5 开发者支持

| 编号 | 需求 | 优先级 |
|---|---|---|
| PL-T-1 | 算子 SDK 包：稳定头文件（接口层不含引擎内部头）、CMake 脚手架（保证与引擎 ABI 同构建选项）、元数据打包工具 | P0 |
| PL-T-2 | ABI 对拍检查工具：CI 中用引擎发布包校验 so 元数据与 ABI 版本，不匹配直接失败 | P0 |
| PL-T-3 | so 加载自检工具：不启动完整引擎即可对 so 做加载校验（dry-run） | P1 |

## 5. 非功能需求

| 编号 | 指标 | 目标 |
|---|---|---|
| PN-1 | 单个 so 加载（校验+注册，不含算子静态初始化耗时） | < 50 ms |
| PN-2 | 算子级热升级（加载新版 + 会话切换事务，不含算子自身 Open 预热） | 切换事务沿用全局图变更指标（< 100ms 生效） |
| PN-3 | 卸载等待（引用归零后真正 dlclose） | < 100 ms |
| PN-4 | 加载/卸载对运行图的影响 | 零影响（不加锁阻塞数据面、不触发停顿） |
| PN-5 | 注册表查询（版本/引用关系） | < 1 ms |
| PN-6 | 升级窗口安全性：热升级完成后的 24h 内，因 so 卸载导致的段错误/延迟崩溃为 0（压测口径） | 0 |

## 6. 约束

- **ABI 同构建约束**（已确认）：so 必须与引擎用相同编译器版本、标准库、关键编译选项（RTTI/异常/对齐/_DEBUG 关闭）构建；引擎发布包必须附带 ABI 清单与对拍工具（PL-T-1/2），否则该决策不可运维
- 卸载安全性依赖算子遵守开发规范（无自建线程/静态注册回调等），规范属于算子开发文档，但其**可校验部分**（引用计数、线程探测）由引擎在卸载前强制检查（PL-D-4）
- 多版本共存的 so 允许各自携带重复的第三方依赖，符号冲突处理（如 dlmopen 命名空间 / 版本化符号）属于设计问题，需求仅要求：**多 so 共存时符号冲突不得导致错误绑定**（算子 A 的 so 不得调用到算子 B so 内的同名符号）

## 7. 开放问题

| # | 问题 | 影响 |
|---|---|---|
| Q1 | so 的交付形态：裸 so（依赖库由宿主环境保证）还是带依赖的自包含包（so + 依赖目录 + 资源目录）？后者影响加载校验与符号隔离方案 | PL-A-2 元数据范围 |
| Q2 | 引擎自身升级（ABI 变更）时，存量 so 的兼容窗口承诺：不承诺跨大版本兼容（重新编译）还是承诺 N 个版本的兼容期？ | SDK 稳定性承诺、影响 PL-V 兼容矩阵 |
| Q3 | 强制卸载的"联动变更"（PL-D-3 一键替换）是否纳入首期，还是首期只做"拒绝卸载+人工变更"？ | 工作量与升级收尾体验的取舍 |
| Q4 | 逻辑卸载降级（PL-D-5）是否可接受为常态（即默认永不 dlclose）？若业务可接受，"真卸载"可以降为 P1，实现风险大幅下降 | 需求分层的关键取舍 |
| Q5 | 算子 so 是否允许携带自己的工作线程（如内部线程池），还是必须完全复用引擎 Executor？直接影响 PL-D-4 可实现性 | 算子开发规范核心条款 |

## 8. 验收要点

- 加载：放入 so → API 通知 → 新图可用该算子；ABI 不匹配 so 被拒且错误明确
- 多版本：1.0/2.0 共存，同一会话从 1.0 变更到 2.0，输出无中断（沿用图变更验收），回滚到 1.0 同样成立
- 卸载：引用非零拒绝卸载；引用归零后卸载成功；卸载后 24h 压测无延迟崩溃（PN-6）；重载可用
- 隔离：损坏 so（注册崩溃/超时）被隔离，引擎与其他算子/图不受影响
- 灰度：两图分别用不同版本，互不串扰，审计可查各图版本
- 升级链路：加载 2.0 → 会话切换 → 卸载 1.0 全流程不重启，期间既有会话零丢帧
